## 0. 怎么读这份指导书

### 0.1 一句话说清 lab2 要解决的问题

**一个进程从哪儿来、什么时候变成僵尸、谁给它收尸？**

答案分三层：

1. **视角层**：一个进程 = `proc[]` 数组里的一个槽位（`struct proc`）+ 一个状态。

   全内核只有五个状态（`proc.h:42`）：`UNUSED` / `SLEEPING` / `RUNNABLE` / `RUNNING` / `ZOMBIE`。
      所谓"进程在跑"，在这层看就是**某个槽位的** `state` **等于** `RUNNING`。
2. **机制层**：`fork()` 造进程、`exit()` 让它变僵尸、`wait()` 收尸、

   `yield()` 让位、`sleep()` / `wakeup()` 睡眠唤醒。**这一整层本 lab 一行都不用改。**
3. **接口层**：给用户三个新工具 —— `getppid`（问爸爸是谁）、

   `sched_yield`（主动让位）、`wait4`（认领指定的孩子）。
      **这四个函数体就是你要写的全部内容，加起来不到 60 行。**

lab2 的全部工作，就是让这四个函数各自"接住一个用户请求、翻译成一次已有的内核动作"。

## 2. 专题一：进程控制块

### 2.1 一个进程在内存里长什么样

先扔一个你可能没想过的问题：**内核怎么"记住"一个正在跑的程序？**

它不是记住那段代码（代码在内存里躺着，谁都能读），也不是记住 CPU 寄存器
（寄存器一被换掉就没了）。它记住的是**一个结构体**：

```text
┌──────────────────────────────────────────────────────────────────────────┐
│ 字段            │ 类型            │ 一句话职责                           │
├─────────────────┼─────────────────┼──────────────────────────────────────┤
│ state           │ enum procstate  │ 当前处于五态里的哪一个               │
│ parent          │ struct proc *   │ ★ 指向父进程控制块（不是 pid！）     │
│ pid             │ int             │ 进程 ID，全局唯一                    │
│ xstate          │ int             │ 退出码，留给父进程 wait / wait4 读   │
│ chan            │ void *          │ 睡在哪个「信道」上（专题五的关键）   │
│ killed          │ int             │ 被 kill 过的标记                     │
│ sz / pagetable  │ uint64 / ptr    │ 地址空间多大 / 怎么翻页（lab4 主角） │
└──────────────────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────────────────┐
│ ★ 上表前六项都在 struct proc 的「p->lock 保护」区（proc.h:48 起）；      │
│    sz / pagetable / ofile / name 在「本进程私有」区，不必持锁。          │
│    本 lab 只碰前六项 —— 它们全都是会说谎的状态：                         │
│    必须持 p->lock 读，否则你读到的是别的 CPU 正在改的旧值。              │
└──────────────────────────────────────────────────────────────────────────┘
```

看几件容易被跳过的事：

🧠 `parent` **是「指针」，不是「pid」**（`proc.h:50`）。
所以 `getppid` 要走三步解引用：`myproc()` → `->parent` → `->pid`。
如果你以为它是一个整数 pid，专题八的 CP① 你大概率会写成 `return myproc()->parent;` ——
编译能过（`int` 和指针在警告级别下未必报错），跑起来返回一个地址。

🧠 `struct proc` **被一刀切成两半**（`proc.h:48` / `:56`）。
上半段的六个字段（`state` / `parent` / `chan` / `killed` / `xstate` / `pid`）
**全部必须持** `p->lock` **才能读**，因为它们会被别的 CPU 在背后改。
下半段（`sz` / `pagetable` / `ofile` / `name` / `tmask` …）只属于这个进程自己，
不必持锁。本 lab 的四个 CP 只碰上半段 —— 而"要持锁"这件事，
正是 CP③B 那几个细节（锁在循环外、`chan` 必须是那个指针）的根源。

🧠 `proc[]` **是个固定大小的数组**（`kernel/proc.c:20`，长度 `NPROC = 50`，`param.h:4`）。
所以"造一个进程"不是 `malloc` 一个结构体，而是**在这 50 个槽位里抢一个** `state == UNUSED` **的**。
`allocproc()` 干的就是这件事（`proc.c:127`，真正分配 pid 在 `:142`）。

### 2.2 进程树：你的程序站在哪一层

```text
┌────────────────────────────────────────────────────────────┐
│ init（pid=1，proc.c:285 userinit 创建）                    │
│ ★ 它从没被赋过 parent（proc.c:127 allocproc 不设这个字段） │
│    所以 init 的 parent 是 NULL —— 这是 CP① 的天然边界      │
└────────────────────────────────────────────────────────────┘
                               │  你每天面对的那一层
                               ▼
┌────────────────────────────────────────────────────────────┐
│ sh（init 的第一个子进程，parent 指向 init）                │
│   就是 lab0 里你敲命令的那个 shell                         │
└────────────────────────────────────────────────────────────┘
                               │  本 lab 的验收程序
                               ▼
┌────────────────────────────────────────────────────────────┐
│ proctest（sh fork 出来的子进程）                           │
│   parent 指向 sh → 所以 getppid() 应当返回 sh 的 pid       │
│   它再 fork 一个孩子，那个孩子的 parent 指向 proctest      │
└────────────────────────────────────────────────────────────┘
```

⚠️ `init` **的** `parent` **是** `NULL`**。** 这一条是本 lab 最值钱的边界知识：

- `allocproc()` 从头到尾**没有**给新控制块设过 `parent`（`proc.c:127` 到 `:168` 之间没有这一行）；
- `userinit()` 也没设（`proc.c:285` 到 `:311` 之间同样没有）；
- 真正给 `parent` 赋值的**只有** `fork()` **一处**（`proc.c:355`）。

于是 `init` 这个"第一个进程"的 `parent` 就一直是 0（NULL）。
**CP① 的标准答案** `return myproc()->parent->pid;` **对** `init` **会解空指针。**
而 `proctest` 抓不到这一条 —— 因为它跑在 `sh` 之下，`parent` 永远不为空。
这就是后面专题八要讨论的"极简实现的边界"。

### 2.3 五个状态

```text
┌───────────────────────────────────────────────────────────────────────────┐
│ 状态      │ 含义                        │ 谁会把你变成它                  │
├───────────┼─────────────────────────────┼─────────────────────────────────┤
│ UNUSED    │ 控制块空闲，可以被分配      │ freeproc（proc.c:193）          │
│ RUNNABLE  │ 准备好了，排队等 CPU        │ userinit / fork / yield         │
│           │                             │ wakeup / wakeup1 / kill         │
│ RUNNING   │ 正在某个 CPU 上执行         │ scheduler（proc.c:576）         │
│ SLEEPING  │ 阻塞等一个事件（子进程退出  │ sleep（proc.c:680）             │
│           │ 等）                        │                                 │
│ ZOMBIE    │ ★ 已退出，但父进程还没来收  │ exit（proc.c:464）              │
│           │ 尸                          │                                 │
└───────────────────────────────────────────────────────────────────────────┘

┌───────────────────────────────────────────────────────────────────────────┐
│ ★ ZOMBIE 是这一 lab 的题眼：进程已经死了，但控制块还占着。                │
│    它占着的唯一原因 —— 退出码 xstate 还没被父进程取走。                   │
│    所以 wait4 的核心动作是：先把 xstate 写回用户态，再回收控制块。        │
│    这两步的顺序一颠倒，退出码就永远丢了（见专题六）。                     │
└───────────────────────────────────────────────────────────────────────────┘
```

🧠 **五个状态的定义在** `proc.h:42` **的** `enum procstate` **里，顺序就是它们在内存里的编号**：
`UNUSED` = 0、`SLEEPING` = 1、`RUNNABLE` = 2、`RUNNING` = 3、`ZOMBIE` = 4。
在 gdb 里 `p p->state` 打出来的是数字，你需要自己对照这张表（专题七会用到）。

### 2.4 十处写点：状态从来不会"自己"变

```text
┌───────────────────────────────────────────────────────────────────────┐
│ 边          │ 触发者                 │ 写点        │ 要持 p->lock 吗  │
├─────────────┼────────────────────────┼─────────────┼──────────────────┤
│ → RUNNABLE  │ userinit（首个进程）   │ proc.c:303  │ 要（已持）       │
│ → RUNNABLE  │ fork（子进程）         │ proc.c:376  │ 要               │
│ → RUNNABLE  │ yield（CP② 走这里）    │ proc.c:631  │ ★ 要，它自己加   │
│ → RUNNABLE  │ wakeup（被唤醒）       │ proc.c:704  │ 要               │
│ → RUNNABLE  │ wakeup1（被唤醒）      │ proc.c:718  │ 要               │
│ → RUNNABLE  │ kill（唤醒睡眠者）     │ proc.c:736  │ 要               │
│ → RUNNING   │ scheduler 选中         │ proc.c:576  │ 要               │
│ → SLEEPING  │ sleep                  │ proc.c:680  │ 要               │
│ → ZOMBIE    │ exit                   │ proc.c:464  │ 要               │
│ → UNUSED    │ freeproc 回收          │ proc.c:193  │ 要               │
└───────────────────────────────────────────────────────────────────────┘

┌───────────────────────────────────────────────────────────────────────┐
│ ★ 十处写点里，本 lab 的主角是 yield 写 RUNNABLE（CP②），              │
│    exit 写 ZOMBIE、freeproc 写 UNUSED（CP③B 要把它们串起来）。        │
│    ★ 注意 allocproc 自己一行 state 都不写（:127-:168）：              │
│      它只把控制块准备好，谁把它变成 RUNNABLE 由调用者决定             │
│      （userinit :303 或 fork :376）——「谁创建谁设状态」。             │
│    看一眼这张表你会发现：状态切换从来没有「不加锁」的先例 ——          │
│    这就是为什么 CP② 的正确写法是复用 yield()，而不是自己改 state。    │
└───────────────────────────────────────────────────────────────────────┘
```

这张表建议你盯着看三十秒。它的分量在于：

- `state` 这个字段在全内核只有 **10 个写点**；
- 其中 **6 个**是在写 `RUNNABLE`（`userinit` / `fork` / `yield` / `wakeup` / `wakeup1` / `kill`），但只有 `yield`（`proc.c:631`）是从 `RUNNING` 改回 `RUNNABLE` 的；
- **没有一条边是不持锁写下去的** —— 一个例外都没有。

### 2.5 小结与练习

- 一个进程 = `proc[]` 的一个槽位；`state` 是它的灵魂字段，全内核只有 10 个写点。

外加一条 `RUNNING → SLEEPING → RUNNABLE` 的旁路（睡眠）。

## 3. 专题二：`fork` —— 一次调用，两次返回

### 3.1 六个步骤

`fork()` 是你写过的第一个"长得不像函数"的函数。它的全部代码在 `proc.c:336`，
我们按执行顺序拆成六步：

```text
┌────────────────────────────────────────────────────────────────────┐
│ ① allocproc()　proc.c:127                                          │
│    在 proc[] 里找一个 state == UNUSED 的控制块，分配新 pid（:142） │
└────────────────────────────────────────────────────────────────────┘
                                   │
                                   ▼
┌────────────────────────────────────────────────────────────────────┐
│ ② 复制地址空间　uvmcopy                                            │
│    把父进程的每一页内存复制一份给孩子（子进程的 sz 稍后单独设）    │
└────────────────────────────────────────────────────────────────────┘
                                   │  所以它「继续执行」的位置也相同
                                   ▼
┌────────────────────────────────────────────────────────────────────┐
│ ③ 复制 trapframe                                                   │
│    用户态的全部寄存器快照整份抄过来 —— 孩子开局和爸爸一模一样      │
└────────────────────────────────────────────────────────────────────┘
                                   │  parent 是个指针
                                   ▼
┌────────────────────────────────────────────────────────────────────┐
│ ④ np->parent = p　★ proc.c:355                                     │
│    子进程在这里认爸爸。这一行就是 CP① 能工作的全部前提             │
└────────────────────────────────────────────────────────────────────┘
                                   │  ★ 两次返回的全部秘密
                                   ▼
┌────────────────────────────────────────────────────────────────────┐
│ ⑤ 把 a0 改写成 0                                                   │
│    父进程的 a0 保留子进程 pid；子进程的 a0 被清成 0                │
└────────────────────────────────────────────────────────────────────┘
                                   │
                                   ▼
┌────────────────────────────────────────────────────────────────────┐
│ ⑥ np->state = RUNNABLE　proc.c:376                                 │
│    子进程进入待跑队列，等 scheduler 挑中它                         │
└────────────────────────────────────────────────────────────────────┘
```

🧠 **第③步是"两次返回"的全部秘密**：`fork` 把父进程的 `trapframe` 整份抄给孩子
（`proc.c:361`），所以孩子"看起来"也在等 `fork` 返回 —— 因为它的寄存器快照
就是爸爸在 `ecall` 那一刻的快照。
然后 `fork` 把**孩子的** `a0` 改成 0（`proc.c:364`），父进程的 `a0` 不动。
`ecall` 的返回值约定是"放在 `a0` 里"，于是：

- 父进程读到的 `fork()` 返回 = `a0` = 子进程 pid（`:380` 返回 `pid`）；
- 子进程读到的 `fork()` 返回 = `a0` = 0。

**全程** `fork` **只返回了一次。** 你看到的是两个不同进程各自的返回值。

### 3.2 「两次返回」到底长什么样

## 4. 专题三：`exit` → `ZOMBIE` → `freeproc` → `UNUSED`

### 4.1 `exit` 的六笔动作

一个进程"死了"要经过很多笔动作，`exit()` 在 `proc.c:413`。顺序不能乱：

```text
┌──────────────────────────────────────────────────────────┐
│ ① 关掉所有打开的文件　proc.c:421-427                     │
│    遍历 ofile[0..NOFILE)，逐个 fileclose，再把槽位清 0   │
│    顺手 eput(p->cwd) 放掉当前目录（:429）                │
└──────────────────────────────────────────────────────────┘
                              │  宁可多叫一次
                              ▼
┌──────────────────────────────────────────────────────────┐
│ ② 先把 init 叫醒　proc.c:437-439                         │
│    因为可能有孩子要被托孤给 init —— 它得醒着才能收到     │
└──────────────────────────────────────────────────────────┘
                              │
                              ▼
┌──────────────────────────────────────────────────────────┐
│ ③ 抓住爸爸并先锁住它　proc.c:448 / :453                  │
│    original_parent = p->parent，然后 acquire 它的锁      │
│    锁序规定：父进程的锁必须先于子进程的锁                │
└──────────────────────────────────────────────────────────┘
                              │  ★ 信道必须是那个 proc 指针
                              ▼
┌──────────────────────────────────────────────────────────┐
│ ④ 托孤 + 叫醒爸爸　proc.c:458 / :461                     │
│    reparent(p) 把自己的孩子全交给 init                   │
│    wakeup1(original_parent) 唤醒睡在 wait/wait4 上的爸爸 │
└──────────────────────────────────────────────────────────┘
                              │
                              ▼
┌──────────────────────────────────────────────────────────┐
│ ⑤ 最后两笔　proc.c:463 / :464                            │
│    p->xstate = status　　← 退出码留在这里等爸爸来取      │
│    p->state = ZOMBIE　　← ★ 从现在起它就是僵尸了         │
└──────────────────────────────────────────────────────────┘
                              │
                              ▼
┌──────────────────────────────────────────────────────────┐
│ ⑥ sched()　proc.c:469                                    │
│    交出自己的锁、跳进调度器，永不返回（下一行是 panic）  │
└──────────────────────────────────────────────────────────┘
```

🧠 **第②笔（先叫醒** `init`**，**`proc.c:437-439`**）看着多余，其实是有意为之。**
注释（`:432-436`）解释了原因：因为马上要托孤给孩子，而托孤的对象是 `init`，
所以 `init` 必须醒着。但此刻还没法精确判断"到底需不需要托孤"，
于是干脆**不管需不需要都叫一次** —— 多余的唤醒是"无害的"（harmless spurious wakeup）。
这是典型的工程取舍：**宁可多叫一次，不要少叫一次。**

🧠 **第③笔为什么要先抓一份** `original_parent`**（**`proc.c:448`**）？**
注释给了答案：因为可能在自己等待父进程锁的期间，父进程把我"送给了" `init`。
所以得先把"我原来那个爸爸"记下来，才能保证解锁的是同一把锁。

🧠 **第⑤笔的两行必须按这个顺序**（`:463` 写退出码、`:464` 写状态）。
下一节专门讲这个顺序为什么值钱。

### 4.2 两笔写、两笔擦：退出码的生命周期

```text
┌───────────────────────────────────────────────────────────────────────────┐

├─────────────────┼───────────────────┼──────────────┼──────────────────────┤
│ exit 写退出码   │ xstate = status   │ proc.c:463   │ 状态还是 RUNNING     │
│ exit 写状态     │ state = ZOMBIE    │ proc.c:464   │ ★ 变僵尸，等爸爸收   │
```

⚠️ **这是本 lab 最容易被写反的地方。** 看第三行：

`freeproc()` 在 `:192` 会把 `xstate` 清成 0。所以 `wait4` 必须**先**把退出码写回用户态、
**再**调 `freeproc`。顺序一颠倒，用户拿到的 `status` 永远是 0。

而这个错误 `proctest` **能抓到**（`:45` 判 `status != 42`），
但它只会打印一行 `wait4 FAILED`，**不会告诉你"是顺序反了"**。
所以这一节你要记住的不是"不要写反"，而是**"写反了以后报错长什么样"**。

## 5. 专题四：`sched_yield` —— 主动让出 CPU

### 5.1 两种"让位"：被逼的和自愿的

在 lab2 之前，你看到的所有调度都是**抢占式**的：时钟中断到了，内核不许你商量。
lab2 要你补的是另一条路 —— **协作式**：

```text
┌─────────────────────────────┐     ┌─────────────────────────────┐
│  抢占式（内核对你不客气）   │     │   协作式（你自己说让位）    │
├─────────────────────────────┤     ├─────────────────────────────┤
│ 谁发起：时钟中断            │     │ 谁发起：用户程序自己        │
│ 什么时候：时间片到了        │     │ 什么时候：我暂时没活干      │
│ 用户有选择权吗：没有        │     │ 用户有选择权吗：有          │
│ 内核路径：                  │     │ 内核路径：                  │
│   trap → devintr → yield()  │     │   ecall → sys_sched_yield   │
│ → sched() → scheduler()     │     │   → yield() → sched()       │
├─────────────────────────────┤     ├─────────────────────────────┤
│ lab2 之前，你看到的全是这种 │     │ ★ CP② 要你补的就是这条路    │
└─────────────────────────────┘     └─────────────────────────────┘
```

🧠 这两条路**最后汇到同一个地方**：`yield()`。这是内核里非常典型的一种写法 ——
**"谁发起"和"做什么"分开**。时钟中断发起的时候，它不知道你是谁；
用户 `ecall` 发起的时候，它也不知道时间片到没到。
但两者要做的动作完全一样：把自己的状态改回 `RUNNABLE`，然后进调度器。
所以这个动作被提取成了一个函数，两条路都调它。

**这就是 CP② 只有两行的原因，也是它最大的坑的来源**（见专题八的假通 A）。

### 5.2 `yield` 的四行

```text
┌──────────────────────────────────────────────────────┐
│ ① acquire(&p->lock)　proc.c:630                      │
│    改自己的 state 之前必须持自己的锁                 │
└──────────────────────────────────────────────────────┘
                            │  从「在跑」变回「排队」
                            ▼
┌──────────────────────────────────────────────────────┐
│ ② p->state = RUNNABLE　proc.c:631                    │
│    ★ 把 RUNNING 改回 RUNNABLE   │
└──────────────────────────────────────────────────────┘
                            │
                            ▼
┌──────────────────────────────────────────────────────┐
│ ③ sched()　proc.c:632                                │
│    把自己的上下文存进 p->context，swtch 回调度器     │
│    等下次被选中，会从 swtch 的下一行继续 —— 也就是 ④ │
└──────────────────────────────────────────────────────┘
                            │
                            ▼
┌──────────────────────────────────────────────────────┐
│ ④ release(&p->lock)　proc.c:633                      │
│    回到这里说明你又被调度上了，交还锁，函数返回      │
└──────────────────────────────────────────────────────┘
```

🧠 **第②行（**`proc.c:631`**）是全内核唯一一处把** `RUNNING` **改回** `RUNNABLE` **的地方。**
你在 2.4 那张「十处写点」的表里见过它 —— 现在你知道它为什么必须存在了：
**没有它，一个进程一旦被调度上 CPU 就永远不会下来。**（抢占式让位也走这里。）

🧠 **第③行** `sched()` **之后的那一行，要等到"下次被调度上"才会执行。**
这是 `swtch` 最反直觉的地方：`sched()` 看起来像个普通函数调用，
但它里面那句 `swtch` 会把当前上下文整个换掉。等你再次被选中时，
CPU 从 `swtch` 的"返回点"继续走 —— 也就是 `proc.c:633` 的 `release`。

### 5.3 为什么不能自己写 `acquire` + 改 `state` + 调 `swtch`

`yield()` 一共四行，你可能想：那我不用它，自己在 `sys_sched_yield` 里写这四行不就完了？

`proc.c:606` 的 `sched()` 里有四道"守门"，任何一条不满足就是**内核 panic**：

```text
┌───────────────────────────────────────────────────────────────────────────┐
│ 序号  │ 守门条件（不满足就 panic）    │ panic 文本          │ 行号        │
├───────┼───────────────────────────────┼─────────────────────┼─────────────┤
│ ①     │ 必须持着自己的 p->lock        │ sched p->lock       │ 611 / 612   │
│ ②     │ 这一层只能持有一把锁          │ sched locks         │ 613 / 614   │
│ ③     │ 不能以 RUNNING 状态进来       │ sched running       │ 615 / 616   │
│ ④     │ 中断必须关着                  │ sched interruptible │ 617 / 618   │
│ ⑤     │ 保存现场：swtch(&p->context)  │ ——                  │ 621         │
└───────────────────────────────────────────────────────────────────────────┘

┌───────────────────────────────────────────────────────────────────────────┐
│ ★ 这四条守门的含义：sched() 是一段「不允许被打扰」的临界区。              │
│    所以 yield() 的前两步（加锁 + 改 state）正好把 ①②③ 都满足了，          │
│    中断关着满足 ④。                                                       │
│    → 你在 CP② 里自己写 acquire / 改 state / swtch 是危险的：              │
│      少满足一条就是内核 panic，而不是一个温和的错误码。                   │
└───────────────────────────────────────────────────────────────────────────┘
```

⚠️ 注意第⑤行：真正的现场保存发生在 `proc.c:621`，函数名叫 `swtch`
（**没有元音** `i`，全名 switch 被省掉了两个字母 —— 这是 xv6 的命名习惯）。

**结论**：`yield()` 的前两步（加锁 + 改 `state`）正好满足了守门 ①②③，
中断关着满足 ④。你自己写的时候少满足一条，得到的是 panic，
**不是**一个温和的错误码。所以 CP② 是"照抄式"的正确答案 —— 而这也正是它难被检测的原因：
把 `yield()` 删掉，程序照样打印 `passed`。

### 5.4 同一个函数，两个方向

`swtch` 在"进程 → 调度器"和"调度器 → 进程"两个方向上被调用，用的是同一个函数：

```text
┌──────────────────────────────────────────────────────────────┐
│ 进程上下文：yield() 里调用 swtch(&p->context, &cpu->context) │
│ 　把 ra / sp / s0~s11 存进 p->context，然后跳到调度器        │
└──────────────────────────────────────────────────────────────┘
                                │
                                ▼
┌──────────────────────────────────────────────────────────────┐
│ 调度器循环（proc.c:557）                                     │
│ 　挑一个 RUNNABLE 的进程 p → p->state = RUNNING → 切页表     │
└──────────────────────────────────────────────────────────────┘
                                │  第二次：调度器 → 新进程
                                ▼
┌──────────────────────────────────────────────────────────────┐
│ 调度器上下文：swtch(&cpu->context, &p->context)              │
│ 　把调度器自己的现场存进 cpu->context，                      │
└──────────────────────────────────────────────────────────────┘
                                │  ★ 同一个函数，两个方向
                                ▼
┌──────────────────────────────────────────────────────────────┐
│ 　从新进程的 p->context 恢复 ra / sp / s0~s11                │
│ 　于是「看起来像从 swtch 返回了」—— 其实是被换了个人在跑     │
└──────────────────────────────────────────────────────────────┘
```

🧠 记住一句话：`swtch` **可以"看起来像从函数返回"，但它其实是被换了个人在跑。**
这一点在专题七用 gdb 单步时你会亲眼看到：`sched()` 里跳进 `swtch`，
再"出来"的时候，`p->pid` 已经不是刚才那个进程了。

## 6. 专题五：`wait4` —— 父与子的会合点

### 6.1 `wait` 的五个阶段

`sleep(p, &p->lock)` 这一行在 `proc.c:522`，它已经是整段代码的最后一步了。
先把 `wait()`（`proc.c:476`）拆开看 —— 你要写的 `wait4` 就是它的"加强版"：

```text
┌─────────────────────────────────────────────────────────────────────┐
│ ① 先把自己锁住，再进死循环　proc.c:484 / :486                       │
│ acquire(&p->lock) 放在循环外面，整个等待过程一把锁握到底            │
└─────────────────────────────────────────────────────────────────────┘
                                   │
                                   ▼
┌─────────────────────────────────────────────────────────────────────┐
│ ② 扫描整张 proc[] 找自己的孩子　proc.c:489-513                      │
│ if(np->parent == p)（:493）—— 看它时不加 np->lock（:490-:492 注释） │
│ 命中后 acquire(&np->lock)（:496）、havekids = 1（:497）             │
└─────────────────────────────────────────────────────────────────────┘
                                   │  ★ 只有这一条路会返回 pid
                                   ▼
┌─────────────────────────────────────────────────────────────────────┐
│ ③ 如果它已经是 ZOMBIE　proc.c:498-509                               │
│ 记下 pid → copyout2 写回 xstate → freeproc 回收 → 返回 pid          │
└─────────────────────────────────────────────────────────────────────┘
                                   │
                                   ▼
┌─────────────────────────────────────────────────────────────────────┐
│ ④ 扫完一圈：没有孩子 or 自己被 kill　proc.c:516-519                 │
│ 释放两把锁，返回 -1                                                 │
└─────────────────────────────────────────────────────────────────────┘
                                   │  ★ 这里是「丢失唤醒」的防线
                                   ▼
┌─────────────────────────────────────────────────────────────────────┐
│ ⑤ 否则：有孩子但都还活着　proc.c:522                                │
│ sleep(p, &p->lock) —— 释放 p->lock 去睡，等 exit 唤醒               │
└─────────────────────────────────────────────────────────────────────┘
```

⚠️ **第①步"锁在循环外面"是最容易被改坏的地方。** 为什么不能把
`acquire(&p->lock)` 放进循环里？因为会产生**丢失唤醒**：

> 你扫完一圈、发现孩子还活着、准备去睡 —— 就在这**一瞬之间**，
> 孩子在另一个 CPU 上退出了，`exit` 调 `wakeup1(original_parent)`，
> 那时你还没睡下，这次唤醒找不到人；然后你才睡下，**再也没有人来叫你**。

整把锁握到底，就堵死了这个空隙。这也是 `wait` 里那句注释（`proc.c:482-483`）的原话。

🧠 **第②步「看** `np->parent` **时不加** `np->lock`**」是另一个反直觉点**（判断在 `:493`，
注释在 `:490-:492`）：因为 `np` 可能是本进程的祖先，先加 `np->lock` 就违反了
"父先子后"的锁序、会死锁。而 `np->parent` 只由父进程改 —— 此刻我们就是那个父进程，
所以在持着 `p->lock` 的前提下读它是安全的。注释里那句
`// because only the parent changes it, and we're the parent.`（`proc.c:497` 上方）
就是这层推理。

### 6.2 `wait` 与 `wait4` 的唯一差别

```text
┌──────────────────────────────┐     ┌──────────────────────────────┐
│    wait(addr)　proc.c:476    │     │ wait4(pid, addr)　proc.c:540 │
├──────────────────────────────┤     ├──────────────────────────────┤
│ 等「任意一个」子进程         │     │ 等「指定的那个」子进程       │
│ 筛选条件只有一条：           │     │ 筛选条件多一个或：           │
│   if(np->parent == p)        │     │   if(np->parent == p         │
│ 函数签名带 addr              │     │      && (pid == -1           │
├──────────────────────────────┤     │          || np->pid == pid)) │
│ xv6 原生版本                 │     ├──────────────────────────────┤
│ 用户接口：int wait(int*)     │     │ ★ 你的 CP③B，只有这一处不同  │
└──────────────────────────────┘     └──────────────────────────────┘
```

**就这一处。** 你的 CP③B 就是把 `wait()` 的循环抄过来，把筛选条件从
`if(np->parent == p)` 改成 `if(np->parent == p && (pid == -1 || np->pid == pid))`。

⚠️ 但**参数从哪来**是 CP③A 的事。这里有一个最容易写错的地方：

```c
// 用户态调用是 wait4(pid, &status)
// 两个实参分别落在 a0 和 a1 两个槽位
argint(0, &pid);            // ← a0：pid
argaddr(1, &status_addr);   // ← a1：&status（用户态地址）
```

**下标不能写反。** 写反了会怎样？如果 `pid` 槽位里取到一个巨大的数当"用户地址"、
`&status` 槽位里取到一个小整数当 pid，那么 `wait4` 会去找一个 pid 为
`0x3fffff...` 的孩子 —— 找不到，返回 `-1`，`proctest` 打印 `wait4 FAILED`。
报错很长，但**不指向你写错的那一行**。

### 6.3 `chan` 为什么必须是那个指针

`sleep` 的契约是「**把锁交给它**」，而 `wakeup1` 的匹配规则是**指针值完全相等**：

```text
┌──────────────────────────────────────────────────────────────────────────┐
│ 哪一边         │ chan 参数是什么                        │ 行号           │
├────────────────┼────────────────────────────────────────┼────────────────┤
│ 睡下去的一方   │ sleep(p, &p->lock)                     │ proc.c:522     │
│ 被叫醒的一方   │ wakeup1(original_parent)               │ proc.c:461     │
│ 两者必须相等   │ 都是「那个 struct proc 指针」          │ ——             │
└──────────────────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────────────────┐
│ ★ wakeup1 的匹配规则是 chan 指针值完全相等，没有别的关系。               │
│    所以 sleep 的第一个实参必须正好是那个进程控制块的地址。               │
│    常见错法：写成 sleep(&p, &p->lock)。                                  │
│    &p 是「栈上这个局部指针变量」的地址，取值 A。                         │
│    exit 唤醒的是地址 B（控制块本身）→ 两边永远对不上 → 挂死。            │
│    这个错会让 proctest 卡住不动（不是打印 FAILED），而且很难查。         │
└──────────────────────────────────────────────────────────────────────────┘
```

⚠️ `sleep(&p, &p->lock)` **是这一节要你亲手试一次的错法**（专题八的故障注入里有一条）。
`&p` 是"栈上那个局部指针变量 `p` 的地址"，它和"控制块本身的地址"是两个值。
于是 `exit` 唤醒的是地址 B，你睡在地址 A —— **两边永远对不上**。

后果不是打印错误，而是**整台机器卡住不动**（`proctest` 挂死、QEMU 窗口没有新输出）。
专题七会告诉你怎么用 gdb 的 `Ctrl-C` + `bt` 从这种挂死里脱身。

### 6.4 锁序

```text
┌──────────────────────────────────────────────────────────────────────────┐
│ 动作                   │ 持哪些锁           │ 为什么这样安排             │
├────────────────────────┼────────────────────┼────────────────────────────┤
│ 进循环前               │ p->lock            │ 整个等待过程一把锁握到底   │
│ 看 np->parent == p     │ 只持 p->lock       │ ★ 只有父进程会改 np->      │
│                        │                    │ parent                     │
│ 确认命中后             │ 再加 np->lock      │ 父 → 子的固定顺序          │
│ copyout2 / freeproc    │ 两把都持           │ 写回与回收不能被别的 CPU   │
│                        │                    │ 插进来                     │
│ sleep 前               │ 释放 p->lock       │ sleep 的契约：             │
│                        │                    │ 必须把锁交给它             │
└──────────────────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────────────────┐
│ ★ 第三行是反直觉的一步：为什么看 np->parent 时不先加 np->lock？          │
│    proc.c:490 的注释给了答案 —— 「np 可能是本进程的祖先，                │
│    先加 np->lock 就违反了父先子后的顺序，会死锁」。                      │
│    而 np->parent 只由父进程改，此刻我们就是那个父进程，                  │
│    所以在持着 p->lock 的前提下读它是安全的。                             │
└──────────────────────────────────────────────────────────────────────────┘
```

🧠 这一节最值钱的不是"要加锁"，而是**为什么某个地方居然不加锁**。
表里第三行（看 `np->parent` 时只持 `p->lock`）是全表唯一一处"看起来漏了锁"的地方 ——
而它恰恰是**必须**这么写，否则死锁。

## 7. 专题六：用户态指针与 `copyout2`

### 7.1 用户传进来的那个地址，内核不能直接用

`wait4(pid, &status)` 的第二个参数，从用户的角度看是"一个 `int` 的地址"。
可这个数字到了内核里，它是一个**用户地址空间里的虚拟地址**：

```text
┌────────────────────────────────────────────────────────────────────┐
│ 用户态：int status = -1;                                           │
│ 内核态：argaddr(1, &status_addr) 拿到 0x3fff... 这样一个数         │
│ 这个数字是「用户自己地址空间里的地址」，不是物理地址               │
└────────────────────────────────────────────────────────────────────┘
                                   │  ★ 三种翻车
                                   ▼
┌────────────────────────────────────────────────────────────────────┐
│ 内核凭什么不能直接 *(int *)status_addr = 42 ?                      │
│ ① 内核此刻跑在内核页表上，那个地址在页表里未必有映射               │
│ ② 即使有，也可能属于别的进程（内核页表里没有进程私有映射时）       │
│ ③ 用户完全可能传一个 0 或 MAXVA 附近的坏地址进来                   │
└────────────────────────────────────────────────────────────────────┘
                                   │
                                   ▼
┌────────────────────────────────────────────────────────────────────┐
│ 所以 xv6 定了一条规矩：                                            │
│ 内核要写用户内存，必须走 copyout 系列接口，不许自己解引用          │
└────────────────────────────────────────────────────────────────────┘
                                   │
                                   ▼
┌────────────────────────────────────────────────────────────────────┐
│ 本 lab 用的版本：int copyout2(uint64 dstva, char *src, uint64 len) │
│ 声明在 kernel/include/vm.h:31，实现在 kernel/vm.c:446              │
└────────────────────────────────────────────────────────────────────┘
```

⚠️ 三种翻车，每一条都真实发生过：

1. 内核此刻跑在内核页表上，那个地址在**当前页表**里未必有映射；
2. 就算有映射，也可能是**别的进程**的（想想调度器切页表的时刻）；
3. 用户完全可以传一个 `0` 或者 `MAXVA`（`riscv.h:365`）附近的坏地址进来 ——

   内核如果不检查就写下去，等于让用户**随手改掉内核内存**。

所以 xv6 定了一条死规矩：**内核要写用户内存，必须走** `copyout` **系列接口，不许自己解引用。**
你的 CP③B 里那一句写回，就必须走这条规矩。

### 7.2 `copyout` 与 `copyout2`

本 lab 用的是 `copyout2`，它和原版 `copyout` 不是"新老版本"的关系，是两个不同的东西：

```text
┌──────────────────────────────────────────────────────────────────────┐
│            │ copyout（原版）           │ copyout2（本 lab 用）       │
├────────────┼───────────────────────────┼─────────────────────────────┤
│ 签名       │ copyout(页表, dstva,      │ copyout2(dstva, src, len)   │
│            │ src, len)                 │                             │
│ 怎么拷     │ 逐页 walkaddr 找物理页再  │ 一次平坦 memmove            │
│            │ memmove                   │                             │
│ 边界检查   │ 靠页表项是否存在          │ ★ 先比 myproc()->sz         │
│ 行号       │ vm.c:424                  │ vm.c:446                    │
│ 失败返回   │ -1                        │ -1                          │
└──────────────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────────────┐
│ ★ 关键差异在第三行。copyout2 的动作只有两步（vm.c:448-452）：        │
│    uint64 sz = myproc()->sz;                                         │
│    if (dstva + len > sz || dstva >= sz) return -1;                   │
│    memmove((void *)dstva, src, len);                                 │
│    它检查的正是 [dstva, dstva+len) 是否落在 [0, sz) 之内 ——          │
│    也就是 lab4 里你亲手推过的那根 sz 分界线。                        │
└──────────────────────────────────────────────────────────────────────┘
```

🧠 `copyout` **是"逐页走页表"的通用版本**（`vm.c:424`）：它用 `PGROUNDDOWN`
算出每一页的起始地址，`walkaddr` 现查物理页，再 `memmove` 一小段。
它不需要知道进程多大 —— 边界检查**天然由"页表里有没有这一项"完成**。

🧠 `copyout2` **是"一次平坦拷贝"的 k210 特化版本**（`vm.c:446`），只有三步：

```c
uint64 sz = myproc()->sz;
if (dstva + len > sz || dstva >= sz) return -1;
memmove((void *)dstva, src, len);
```

它检查的正是 `[dstva, dstva+len)` 是否落在 `[0, sz)` 之内 ——
**也就是 lab4 里你要亲手推的那根** `sz` **分界线**。
如果你已经做过 lab4，这一句会让你会心一笑；如果还没做，记住这个形状，
lab4 会从另一端再讲一遍。

### 7.3 它凭什么敢直接 `memmove`

这是本节最值钱的一个问题：`copyout2` **没有查页表，凭什么？**

```text
┌─────────────────────────────────────────────────────────────────┐
│ copyout2 只做了「比大小 + memmove」，为什么敢直接按虚拟地址拷？ │
│ 因为它赌定了一件事：当前页表下，[0, sz) 是平坦可访问的          │
└─────────────────────────────────────────────────────────────────┘
                                 │  ★ 这是 k210 特有的设计
                                 ▼
┌─────────────────────────────────────────────────────────────────┐
│ k210 版 xv6 为每个进程维护了两张页表（proc.h:59 / :60）：       │
│   pagetable　　用户页表                                         │
│   kpagetable　 内核视角的同一份映射                             │
└─────────────────────────────────────────────────────────────────┘
                                 │
                                 ▼
┌─────────────────────────────────────────────────────────────────┐
│ 调度器切进去之前会切到 p->kpagetable（proc.c:578），            │
│ 于是内核里按用户虚拟地址 memmove 就能落到正确的物理页           │
└─────────────────────────────────────────────────────────────────┘
                                 │
                                 ▼
┌─────────────────────────────────────────────────────────────────┐
│ 所以 copyout2 = 「边界检查 + 一次平坦拷贝」，没有 walkaddr 循环 │
│ 这也解释了为什么它叫 copyout2 而不是 copyout                    │
└─────────────────────────────────────────────────────────────────┘
```

🧠 答案是 **k210 版 xv6 为每个进程维护了两张页表**（`proc.h:59` / `:60`）：

- `pagetable`：用户页表，用户态在跑的时候挂着的就是它；
- `kpagetable`：**同一份映射的内核视角**。

调度器把进程切上 CPU 之前，会先切到 `p->kpagetable`
（`proc.c:578` 的 `w_satp(MAKE_SATP(p->kpagetable))`）。
于是在内核里按"用户虚拟地址"直接 `memmove`，**就能正好落到那个用户页上**。

⚠️ 这也意味着：`copyout2` **的正确性依赖于"调度器已经切了** `kpagetable`**"这个前提。**
你不需要在本 lab 里验证它，但你应该能回答："如果我在一个没跑用户进程的上下文里
调 `copyout2`，会发生什么？"（提示：`myproc()` 是谁。）

### 7.4 先写回，后回收

```text
┌─────────────────────────────────────────────────────────────────┐
│ 找到 ZOMBIE 孩子之后，两件事不能做反：                          │
└─────────────────────────────────────────────────────────────────┘
                                 │  退出码还在
                                 ▼
┌─────────────────────────────────────────────────────────────────┐
│ ① 先 copyout2　proc.c:501                                       │
│ 把 np->xstate 写回用户态 —— 此刻退出码还在结构体里              │
└─────────────────────────────────────────────────────────────────┘
                                 │  退出码被抹掉
                                 ▼
┌─────────────────────────────────────────────────────────────────┐
│ ② 后 freeproc　proc.c:506                                       │
│ 回收控制块。注意 freeproc 会执行 xstate = 0（proc.c:192）       │
└─────────────────────────────────────────────────────────────────┘
                                 │  ★ 能抓到，但不告诉你原因
                                 ▼
┌─────────────────────────────────────────────────────────────────┐
│ 如果颠倒过来：freeproc 先跑                                     │
│ → xstate 已经是 0 → copyout2 拷回去的是 0                       │
│ → 用户看到 status == 0，而 proctest 期望 42 → 打印 wait4 FAILED │
└─────────────────────────────────────────────────────────────────┘
```

这一节其实是专题三那一小节的"落地版"：你终于要亲手把 `copyout2`（`:501`）写在
`freeproc`（`:506`）**前面**。

### 7.5 小结与练习

- 用户态指针在内核里只是"用户地址空间里的一个虚拟地址"，不能裸解引用。

1. **返回** `myproc()->parent` **而不是** `->pid` —— 返回的是指针，`proctest` 打印一个巨大的数。
2. **返回** `myproc()->pid` —— 逻辑上像"照抄 `sys_getpid`"，但它是**自己**的 pid。

   `proctest` 的子进程那一关会失败（`proctest.c:31`）。
3. 忘记 `int` → `uint64` 的返回类型约定：`sys_getppid` 的返回类型是 `uint64`

   （和所有 `sys_*` 一样），但 `parent->pid` 是 `int`，这里是隐式提升，没问题 ——
      但**不要**写成 `return (uint64)myproc()->parent->pid;` 之外的怪东西。

**参考实现（13 行，含空行与注释）**

```c
uint64
sys_wait4(void)
{
  int pid;
  uint64 status_addr;

  if(argint(0, &pid) < 0)
    return -1;
  if(argaddr(1, &status_addr) < 0)
    return -1;

  /* 简化 ABI：-1 等任意子进程；>0 等指定子进程；其余非法 */

    return -1;

```

⚠️ **不要在** `sysproc.c` **里扫** `proc[]` —— 那是 CP③B。

### 9.6 CP③B —— `wait4`（`kernel/proc.c:540`）

```text
┌───────────────────────────────────────────────────────────────────┐
│ 动笔前先定位两个写点：                                            │
│ 　grep -n "ZOMBIE" kernel/proc.c　→ exit 在 :464 写它             │
│ 　grep -n "UNUSED" kernel/proc.c　→ freeproc 在 :193 写它         │
└───────────────────────────────────────────────────────────────────┘
                                  │
                                  ▼
┌───────────────────────────────────────────────────────────────────┐
│ 与 wait()（:476）的差别只有一处 —— 扫描时多一个 pid 过滤：        │
│ 　if(np->parent == p && (pid == -1 || np->pid == pid))            │
└───────────────────────────────────────────────────────────────────┘
                                  │
                                  ▼
┌───────────────────────────────────────────────────────────────────┐
│ 四个必须说清的细节（追问会一个个问）：                            │
│ 　① 锁在循环外面：避免「扫完准备睡」的空隙里子进程 exit 并 wakeup │
│ 　② 看 np->parent 时不加 np->lock：先加会违反父先子后而死锁       │
│ 　③ 先 copyout2 后 freeproc：freeproc 会清 xstate（:192）         │
│ 　④ sleep(p, &p->lock)：chan 必须与 exit 里 wakeup1 的实参同值    │
└───────────────────────────────────────────────────────────────────┘
                                  │
                                  ▼
┌───────────────────────────────────────────────────────────────────┐
│ 参考实现 35 行，主体就是 wait() 的循环加一个或条件                │
└───────────────────────────────────────────────────────────────────┘
```

**参考实现（35 行）**

```c
int
wait4(int pid, uint64 addr)
{
  struct proc *np;
  int havekids, found;
  struct proc *p = myproc();

  acquire(&p->lock);

  for(;;){
    havekids = 0;
    for(np = proc; np < &proc[NPROC]; np++){
      if(np->parent == p && (pid == -1 || np->pid == pid)){
        acquire(&np->lock);
        havekids = 1;
        if(np->state == ZOMBIE){
          found = np->pid;
          /* ★ 先写回，后回收。写回失败就把 ZOMBIE 留着 */
          if(addr != 0 &&
             copyout2(addr, (char *)&np->xstate, sizeof(np->xstate)) < 0){
            release(&np->lock);
            release(&p->lock);
            return -1;
          }
          freeproc(np);
          release(&np->lock);
          release(&p->lock);
          return found;
        }
        release(&np->lock);
      }
    }
    if(!havekids || p->killed){
      release(&p->lock);
      return -1;
    }
    sleep(p, &p->lock);
  }
}
```

**和** `wait()`**（**`proc.c:476`**）对比着读**，你会看到它几乎逐行对应，
只有三处不同：筛选条件多了一个"或"、变量名（`found` 代 `pid`）、以及 `return -1` 的错误路径。

### 9.7 ★ 四种「假通」——不看这一节等于没做这一 lab

**这是本 lab 最重要的教学点。** `proctest` 打印 `lab2 test passed`
**不代表你做对了** —— 下面四种写法里有两种能一路绿灯：

```text
┌─────────────────────────────────────────────────────────────────────────┐
│ 假通       │ 怎么写的                   │ proctest 反应  │ 抓得到吗     │
├────────────┼────────────────────────────┼────────────────┼──────────────┤
│ A（最狠）  │ CP② 只写 return 0，不调    │ 照样 passed    │ ★ 抓不到     │
│            │ yield()                    │                │              │
│ B          │ CP③A 省掉 pid 的语义校验   │ 照样 passed    │ ★ 抓不到     │
│ C          │ CP③B 删掉 sleep，          │ 时快时慢       │ 偶发抓到     │
│            │ 扫不到就返回 -1            │                │              │
│ D          │ CP③B 写成 sleep(&p, ...)   │ 挂死、无输出   │ 能抓到       │
└─────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────┐
│ ★ A 和 B 是本 lab 最值钱的两个坑：程序打印了 passed，                   │
│    但那件事根本没发生 —— sched_yield 没有让出 CPU，                     │
│    wait4 对非法 pid 一点不设防。                                        │
│    proctest 抓不到它们，因为它的判据只覆盖「正常路径」。                │
│    所以本 lab 的验收必须靠追问：说清 yield 做了什么、                   │
│    说清为什么 -1 和正 pid 是两种语义、其余应当拒绝。                    │
└─────────────────────────────────────────────────────────────────────────┘
```

#### 假通 A：CP② 只写 `return 0;`（最狠，完全抓不到）

```c
uint64
sys_sched_yield(void)
{
  return 0;      // ← 忘了调 yield()
}
```

`proctest.c:18` 的判据是 `if(sched_yield() != 0)` —— 它**只看返回值**。
返回 0，判据放过，一路走到 `lab2 test passed`。
**可这件事根本没发生：进程一次都没有主动让出 CPU。**

这是本 lab 唯一一个"**程序打印通过、行为完全没做**"的坑。
它也是 `proctest` 覆盖不到的第 1 件事（见 9.8 那张表）。

#### 假通 B：CP③A 省掉 `pid` 的语义校验（抓不到）

```c
if(argint(0, &pid) < 0)
  return -1;
if(argaddr(1, &status_addr) < 0)
  return -1;
// ← 少了 if(pid != -1 && pid <= 0) return -1;
return wait4(pid, status_addr);
```

`proctest` **只传过** `-1` **和正 pid**（`proctest.c:44` 传的是 `pid`，即子进程的真 pid），
所以它永远不会传 `0` 或 `-2`。少了那一行，测试照样通过，
而"非法输入应当被拒绝"这条语义**没有被实现**。

#### 假通 C：CP③B 删掉 `sleep`，扫不到就返回 `-1`（偶发）

```c
if(!havekids || p->killed){
  release(&p->lock);
  return -1;
}
// ← 少了 sleep(p, &p->lock);
```

如果子进程**碰巧已经退出**了（在父进程扫表之前），你还是能扫到它、还是能通过。
可如果子进程还没退，你就直接返回 `-1` 了。
**这个错的表现是"时快时慢"**：同一份代码连跑 3 遍，可能 2 次通过、1 次失败。

⚠️ 这也解释了为什么验收判据里有一条是「**连跑 3 遍都是同一结果**」。

#### 假通 D：CP③B 的 `sleep` 信道写错（能抓到，但报错很难看）

```c
sleep(&p, &p->lock);      // ← 应该是 sleep(p, &p->lock)
```

`&p` 是栈上局部变量的地址，和解引用出来的 "控制块地址" 不是同一个值。
于是你睡在一个**没人会去叫的信道**上 —— 后果是**挂死、无输出**，
不是 `FAILED`。专题七的 `Ctrl-C` + `bt` 就是为这种情况准备的。

#### 补充：有一种"错误"会抓到，但报错指错地方

把 CP③B 里的 `copyout2` 和 `freeproc` 顺序写反 → `proctest` 会打印
`wait4 FAILED: ... status=0 expected=42`。**它抓到的是"结果不对"，没告诉你"顺序反了"。**
能读懂这条报错指向专题六，才算真懂。

🧠 这三处都**不影响** `proctest` **验收**，也**不要求学生修**（修了也不加分）。

不报错、不影响主路径、被日常测试完整绕过。

其中第**二**处尤其值得想一分钟。我们前面说过：CP① 的"标准答案"只有一行：

```c
return myproc()->parent->pid;
```

**但它对** `init` **进程是错的** —— `init` 的 `parent` 是 `NULL`。
一个"看起来完全正确"的一行实现，在系统的第一个进程上会解空指针。
这就是**"极简实现的边界"**：你写的每一行代码，都有它不曾被测试覆盖到的地方。
本 lab 要你养成的习惯，就是**主动问自己"这一行在什么情况下会不成立"**。
