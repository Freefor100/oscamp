## 0. 怎么读这份指导书

### 0.1 一句话说清 lab1 要你搞清楚什么

**从"机器上电"到"机器断电"，中间到底发生了什么？**

答案分三层（和 lab2 ~ lab7 一脉相承）：

1. **视角层**：整条链路是 8 个站点 —— 加电 → 固件 → 交接 → `_entry` → `main()`
  → 第一个进程 → 用户敲 `halt` → 断电。你能把这 8 个站点连成一串，

  15 个初始化函数、`userinit()` 的 7 步、两张页表、两次 `ecall`。

3. **接口层**：给用户一个新工具 `halt`。**你要写的代码只有 1 行加 1 块注释** ——
  真正的工作量在"说清楚为什么是这样"。这就是本实验和一般编程作业最大的不同。

## 2. 专题一 · 第一条指令在哪里：SBI 加载内核与跳转



### 2.1 先破掉一个根深蒂固的误解

```text
┌─────────────────────────────────────────────────────────────┐
│                    一个必须先破掉的误解                     │
└─────────────────────────────────────────────────────────────┘
                               │  这是「有操作系统之后」的经验
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ ✗ 常见理解（错的）                                          │
│   · 程序 = main() 函数，CPU 加电就从 main 开始跑            │
│   · 栈是「库」帮你准备好的                                  │
│   · 内核一上来就拥有整台机器                                │
└─────────────────────────────────────────────────────────────┘
                               │
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ ✓ 实际发生的（对的）                                        │
│   · 加电瞬间 PC 是硬件定死的复位向量，谁都没在跑            │
│   · 第一个跑起来的是固件，不是内核                          │
│   · 内核是被固件「搬」到内存里、再「跳」进去的              │
└─────────────────────────────────────────────────────────────┘
                               │  ★ 0x1000 不是内存，是 ROM
                               ▼
┌─────────────────────────────────────────────────────────────┐
│        QEMU virt 的复位向量：PC = 0x0000000000001000        │
│ 这块地址在 QEMU 里就是它的 boot ROM，内容是 QEMU 自带的固件 │
└─────────────────────────────────────────────────────────────┘
```

如果你写过 C 程序，你会觉得"程序 = `main()` 函数，CPU 一加电就开始跑 main"。
**在裸机上这是错的**，原因有三条：


| 你以为             | 实际上                                     |
| --------------- | --------------------------------------- |
| 程序从 `main()` 开始 | 从**复位向量**开始。QEMU 的 virt 机器把它定在 `0x1000` |
| 栈是"库"帮你准备的      | 栈要**自己设**（`entry_qemu.S:6-7` 干的就这件事）    |
| 内核一上来就拥有整台机器    | 内核运行在 **S 模式**，最高特权级 M 属于固件             |


🧠 **一个比喻**：内核不是"从零开始造世界"，而是"**从固件手里接过一套已经装修好的房子**"。
固件已经把电通了、把中断控制器配好了、把内存划给你了，
甚至把内核的镜像**搬到了正确的内存地址上**。内核要做的第一件事，是**给自己搭一张椅子（栈）**。

### 2.2 加电瞬间：PC = 0x1000，而且那头什么都没有

⌨️ 先看 lab1 到底怎么启动 QEMU 的（`Makefile:132` / `:135` / `:137`）：

```make
QEMUOPTS  = -machine virt -kernel $T/kernel -m 128M -nographic
QEMUOPTS += -smp $(CPUS)          # CPUS := 2（Makefile:129）
QEMUOPTS += -bios default         # ★ 用 OpenSBI 作为默认固件
```

🧠 **注意** `-kernel` **和** `-bios default` **的分工**：
`-kernel` 告诉 QEMU"把内核镜像放到内存里"，`-bios default` 说"启动时先跑 OpenSBI"。
**QEMU 把这两件事都替你做了** —— 所以在真机上，你需要自己写烧录、自己算加载地址，
而在这里你能少掉一层噪音，专心看内核那一侧。

加电时序是这样的：


| 时刻  | PC           | 在跑什么                    | 特权级 |
| --- | ------------ | ----------------------- | --- |
| 上电  | `0x1000`     | QEMU 的 boot ROM（几十条机器码） | M   |
| 紧接着 | `0x80000000` | **OpenSBI**             | M   |


⚠️ `0x1000` **上并不是内核**，也不是 OpenSBI，而是 QEMU 内置的一小段 ROM。
它干的事极其朴素：把 PC 跳到 `0x80000000`。**这就是"复位向量"的全部含义。**

### 2.3 为什么"内存"这个词在这里要放大看

```text
┌──────────────────────────────────┐   ┌──────────────────────────────────┐
│      「内存」这个概念要放大      │   │     MMIO = Memory Mapped I/O     │
├──────────────────────────────────┤   ├──────────────────────────────────┤
│ 物理地址空间里，RAM 只占中间一段 │   │ 读那个地址 = 读设备寄存器        │
├──────────────────────────────────┤   │ 写那个地址 = 命令设备干活        │
│ 0x1000 是 ROM                    │   ├──────────────────────────────────┤
│ 0x10000000 是串口                │   │ 所以 printf 打印一个字符，       │
│ 0x0C000000 是中断控制器          │   │ 最终就是往 UART 的地址上         │
│ 0x02000000 是定时器 / 中断源     │   │ 写一个字节                       │
├──────────────────────────────────┤   ├──────────────────────────────────┤
│ ★ 外设的寄存器就编在地址里       │   │ ★ 这是「地址观」的第一个         │
│                                  │   │    反直觉之处：地址不一定是内存  │
└──────────────────────────────────┘   └──────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────┐
│ ★ 由此你能自己推出两件事：                                              │
│    ① 内核页表里除了内存，还必须映射这几个外设地址 —— 不然碰不到串口；   │
│    ② 设备地址是【物理】地址，内核里访问它们用的是「偏移映射」           │
│     后的虚拟地址。                                                      │
└─────────────────────────────────────────────────────────────────────────┘
```

🧠 **物理地址空间 ≠ RAM**。这一点如果不掰开，后面看设备映射时会一直别扭：

- `0x0 ~ 0x80000000` 之间的绝大多数格子，**不是内存条，是外设寄存器**；
- 写 `0x10000000` 那个字节，不是"存了一个字节"，而是"**命令串口吐一个字符**"；
- 真正的 RAM 从 `0x80000000` 才开始（`-m 128M` → 到 `0x88000000`）。

所以 `printf` 打印一个字符，最终做的动作是：
**往** `UART` **的地址上写一个字节**。理解了这个，
"设备映射为什么只给 `R|W` 不给 `X`"就顺理成章了 —— 你不需要"执行"设备。

### 2.4 OpenSBI 在 M 模式做了什么

```text
┌─────────────────────────────────────────────────────────────────────────┐
│ #   │ OpenSBI 在 M 模式做的事            │ 为什么内核自己做不到         │
├─────┼────────────────────────────────────┼──────────────────────────────┤
│ 1   │ 设置 M 模式的异常 /                │ 内核是 S 模式，碰不到 M 的   │
│     │ 中断向量（mtvec）                  │ CSR                          │
│ 2   │ 初始化 CLINT 与 PLIC，             │ 只有 M 模式能决定哪些中断给  │
│     │ 配置中断委派规则                   │ S                            │
│ 3   │ 配置 PMP，把内存区域授权给 S 模式  │ 没有 PMP，S                  │
│     │                                    │ 模式连内存都碰不到           │
│ 4   │ 建立自己的运行环境（栈、           │ 此时内核还没开始执行         │
│     │ 解析设备树）                       │                              │
│ 5   │ 准备启动参数：a0 = hartid，a1 =    │ 这是固件与内核的交接单       │
│     │ DTB 地址                           │                              │
│ 6   │ 跳到 0x80200000，把控制权交给内核  │ 这是 S 模式的第一条指令      │
└─────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────┐
│ ★ 记住一句就够：OpenSBI 是内核的「房东」——                              │
│    它先把房子（内存权限、中断路由、设备）收拾好，                       │
│    再把钥匙（控制权）交出去，之后退居幕后。                             │
│    本 lab 最后一步「关机」还得回头求它：内核自己没有断电的能力。        │
└─────────────────────────────────────────────────────────────────────────┘
```

📖 **一句话记住 OpenSBI 的角色**：**它是内核的房东，也是内核唯一能求到的"上级"。**
内核想让机器断电，就得求它（第 7 章会用到）。

🧠 为什么这些事"内核自己做不到"？因为它们全都要碰 **M 模式的 CSR**：

- `mtvec`（M 模式陷阱向量）、PMP（物理内存保护）、CLINT/PLIC 的委派规则、
以及最后的"按电源键"。
- S 模式的代码写这些 CSR 会直接触发非法指令异常 —— **不是权限不够，是根本不认识**。



### 2.5 RISC-V 启动协议：a0 和 a1 的约定

固件交棒的时候，并不是"什么都不说就走"。它按 RISC-V 标准的启动协议（boot protocol）
把两个关键信息（**核编号**与**设备树物理地址**）放在两个寄存器里：

```text
┌───────────────────────────────────┐    ┌───────────────────────────────────┐
│           a0 —— hartid            │    │       a1 —— DTB 的物理地址        │
├───────────────────────────────────┤    ├───────────────────────────────────┤
│ 我是几号核（硬件线程）            │    │ 设备树的物理地址                  │
│ QEMU 用 -smp 2 就是 0 和 1        │    │ 一个 0x8xxxxxxx 附近的值          │
│ ★ 不是 pid，不是线程 ID           │    │ QEMU 会把设备树放在 RAM 里        │
│ 它是硬件上的核编号                │    ├───────────────────────────────────┤
├───────────────────────────────────┤    │ 谁在用：                          │
│ 谁在用：                          │    │ main(hartid, dtb_pa) 的第二个参数 │
│ _entry 用它算自己那份栈           │    │ 本课程不解析设备树，              │
│ main() 用它判断谁是 0 号          │    │ 但你要知道它从哪来                │
└───────────────────────────────────┘    └───────────────────────────────────┘
```

```text
┌────────────────────────────────────────────────────────────────────────┐
│ 对象          │ 是什么                            │ 在本 lab 里的角色  │
├───────────────┼───────────────────────────────────┼────────────────────┤
│ hartid（a0）  │ 硬件线程编号，从 0 起             │ 决定 _entry        │
│               │                                   │ 用哪一段 boot_stac │
│               │                                   │ k                  │
│ DTB（a1）     │ Device Tree Blob，                │ main 的第二个参数  │
│               │ 描述这台机器有哪些设备、          │ （本课程不解析）   │
│               │ 地址是多少                        │                    │
│ boot_stack    │ entry_qemu.S 里 .space 4096*4*2   │ ★ 内核的第一根栈   │
│               │ 的一块 BSS                        │                    │
│ KERNBASE      │ 0x80200000 的宏名（memlayout.h:10 │ 内核代码的物理 /   │
│               │ 2）                               │ 虚拟起点           │
└────────────────────────────────────────────────────────────────────────┘

┌────────────────────────────────────────────────────────────────────────┐
│ ★ 为什么内核一进来就急着建栈？因为紧接着的 `call main` 立刻要用栈 ——   │
│    而此刻内存里没有任何东西替你准备过它。                              │
│    这就是「裸机」两个字的含义：连栈都得自己找一块。                    │
└────────────────────────────────────────────────────────────────────────┘
```

📖 对照代码看 `kernel/main.c:31-32`：

```c
void
main(unsigned long hartid, unsigned long dtb_pa)   /* :32 */
{
  inithartid(hartid);                              /* :34 —— 把 hartid 写进 tp */
```

🧠 **参数是怎么从汇编传过来的？** 这就是 RISC-V 的**函数调用约定**：
第一个参数走 `a0`，第二个走 `a1`。固件并不"认识" `main` 这个函数名 ——
它只是**按约定把值放进 a0/a1，然后跳过去**。`kernel/entry_qemu.S:8` 的 `call main`
正是踩在这个约定上。

⚠️ **易错点**：`hartid` 容易和 `pid` / 线程 ID 混起来。
`hartid` 是**硬件上的核编号**（0 或 1，来自 `-smp 2`），不随进程变；
`pid` 是内核给进程编的号（`proc.c:142`）。**两者毫无关系。**

### 2.6 `_entry`：内核的第一条指令

📖 这是整个内核的第一条指令所在的文件，只有 19 行。

```text
┌────────────────────────────────────────────────────────────────────────────┐
│ 行    │ 指令（entry_qemu.S）   │ 它在干什么             │ 结果             │
├───────┼────────────────────────┼────────────────────────┼──────────────────┤
│ :4    │ add  t0, a0, 1         │ t0 = hartid + 1        │ 先算「第几份」   │
│ :5    │ slli t0, t0, 14        │ t0 = t0 × 16384 = t0   │ 换算成字节偏移   │
│       │                        │ × 16KB                 │                  │
│ :6    │ la   sp, boot_stack    │ 把 boot_stack          │ ★ 还没有分页     │
│       │                        │ 的地址取到 sp          │                  │
│ :7    │ add  sp, sp, t0        │ sp += 偏移量           │ hart1 的栈排在   │
│       │                        │                        │ hart0 后面       │
│ :8    │ call main              │ 跳到 main(hartid,      │ C 代码从这里开始 │
│       │                        │ dtb_pa)                │                  │
│ :10   │ loop: j loop           │ 万一 main              │ 永不返回的兜底   │
│       │                        │ 返回了就原地打转       │                  │
└────────────────────────────────────────────────────────────────────────────┘

┌────────────────────────────────────────────────────────────────────────────┐
│ ★ 这一小段里藏着一个大问题：为什么每颗 hart 要各用一份栈？                 │
│    因为栈里放的是「这一颗核正在干什么」的局部状态；                        │
│    两颗核共用一根栈，等于两个人共用一本记事本 —— 必然写乱。                │
│    ★ 还要注意 :7 是加法不是赋值：boot_stack 是那段空间的【起点】，         │
│      而栈向下生长，sp 最终指向的是它的【顶端】。                           │
│      hart0 拿到 (0+1)×16KB，hart1 拿到 (1+1)×16KB —— 正好各占一段。        │
│      ★ 三处必须一致：.space 4096*4*2 ↔ -smp 2 ↔ NCPU 2（param.h:5）。      │
└────────────────────────────────────────────────────────────────────────────┘
```

```asm
    .section .text
    .globl _entry
_entry:                       /* :3  ★★★ 内核第一条指令在这里 ★★★ */
    add t0, a0, 1             /* :4  t0 = hartid + 1        —— 先算"第几份" */
    slli t0, t0, 14           /* :5  t0 = t0 × 16384        —— 换算成字节偏移 */
    la sp, boot_stack         /* :6  ★ 给 sp 一个物理地址   —— 还没有分页！ */
    add sp, sp, t0            /* :7  sp += 偏移              —— hart1 的栈排在 hart0 后面 */
    call main                 /* :8  跳到 C 世界 */

loop:
    j loop                    /* :10-11  main 万一返回了就在这转圈 */

    .section .bss.stack
    .align 12                 /* :14  按 4KB 对齐 */
    .globl boot_stack
boot_stack:                   /* :16 */
    .space 4096 * 4 * 2       /* :17  32768 字节 = 32KB */
    .globl boot_stack_top
boot_stack_top:               /* :19 */
```

**逐条拆开看，这五条指令各解决一个问题：**


| 行    | 指令                  | 解决什么问题           | 为什么必须这么写                                     |
| ---- | ------------------- | ---------------- | -------------------------------------------- |
| `:4` | `add t0, a0, 1`     | 两个核不能共用一根栈       | hart0 用第 1 份、hart1 用第 2 份，**+1 就是为了避开 0 号份** |
| `:5` | `slli t0, t0, 14`   | 把"第几份"变成"多少字节"   | `14` 是**位移位数**：`1<<14 = 16384`。每个核分 16KB     |
| `:6` | `la sp, boot_stack` | 给 sp 一个**能用的地址** | ⚠️ 此刻**分页还没开**，所以拿到的是**物理地址**                |
| `:7` | `add sp, sp, t0`    | 错开两个核的栈          | 核 0 的栈在低处、核 1 在高处，互不覆盖                       |
| `:8` | `call main`         | 进入 C 代码          | 只用 `a0`/`a1` 传参，所以 `main` 能直接读到 hartid 和 dtb |


🧠 **为什么要** `add t0, a0, 1` **而不是直接** `slli a0, a0, 14`**？**
因为 hart0 的偏移会变成 0，sp 就等于 `boot_stack` 的最底部 ——
而栈是**从高往低长**的，栈底留给自己就立刻越界。
+1 让每个核至少拿到一整份 16KB。

📖 `la` **到底展开成什么？** 这是个很值得深挖的细节：

```text
┌───────────────────────────────────────────────────────────────────┐
│      # la sp, boot_stack  这一行，汇编器实际展开成两条指令：      │
└───────────────────────────────────────────────────────────────────┘
                                  │  ★ 基准是 PC，不是 0
                                  ▼
┌───────────────────────────────────────────────────────────────────┐
│ auipc sp, %pcrel_hi(boot_stack)   ← sp = PC + 高位偏移            │
│ addi  sp, sp, %pcrel_lo(...)      ← sp += 低位偏移                │
└───────────────────────────────────────────────────────────────────┘
                                  │  因为它算的是相对量
                                  ▼
┌───────────────────────────────────────────────────────────────────┐
│ 所以「la 拿到的是哪个地址」取决于「执行到它时 PC 是多少」         │
│ · 开分页前：PC 是物理地址 0x802xxxxx → la 拿到物理地址            │
│ · 开分页后：PC 已被翻译成虚拟地址 → la 拿到虚拟地址               │
│ ★ 同一条 la 指令，语义没变，拿到的东西变了                        │
└───────────────────────────────────────────────────────────────────┘
                                  │
                                  ▼
┌───────────────────────────────────────────────────────────────────┐
│ 这正是「恒等映射」的价值：kvminit 让内核的虚拟地址 == 物理地址，  │
│ 所以开分页前后 PC 的【数值】几乎没变，只有「解释方式」变了。      │
│ 于是同一段机器码在两种世界里都跑得通 —— 中间只差一条 sfence.vma。 │
└───────────────────────────────────────────────────────────────────┘
```

⌨️ **动手小实验（可选，但很推荐）**：编译完在构建目录里跑

```bash
riscv64-unknown-elf-objdump -d target/kernel | sed -n '/<_entry>:/,+12p'
```

你会看到 `la sp, boot_stack` 变成了 `auipc` + `addi` 两条。
**为什么不能用一条** `li`**？** 因为内核的链接地址是 `0x80200000`（`linker/qemu.ld:4`），
这个数塞不进 32 位立即数，必须靠"PC + 偏移"拼出来。

如果没有，跳过这一步，看代码本身即可 —— 不影响你理解。

### 2.7 物理内存：概念、布局、结构

```text
┌─────────────────────────────────────────────────────────────────────────┐
│ 物理地址    │ 这块是什么     │ 大小与说明                               │
├─────────────┼────────────────┼──────────────────────────────────────────┤
│ 0x88000000  │ DRAM 顶端      │ 0x80000000 + 128M = -m 128M 的上界；★    │
│             │                │ 内核没用它                               │
│ 0x80600000  │ PHYSTOP        │ 内核可用物理内存的上界（memlayout.h:105  │
│             │                │ ）                                       │
│ 0x80200000  │ KERNBASE       │ ★ 内核代码起点，_entry 就在这里          │
│ 0x80000000  │ RUSTSBI_BASE   │ ★ 固件 / SBI（OpenSBI），内核的「房东」  │
│ 0x10001000  │ VIRTIO0        │ virtio 磁盘 MMIO（0x1000 字节）          │
│ 0x10000000  │ UART0          │ 串口 MMIO（0x1000 字节）                 │
│ 0x0C000000  │ PLIC           │ 外部中断控制器（0x4000 字节）            │
│ 0x02000000  │ CLINT          │ 定时器 + IPI（0x10000 字节）             │
│ 0x00001000  │ boot ROM       │ ★ 复位向量 PC = 0x1000，加电后从这里开始 │
│ 0x00000000  │ （下界）       │ 物理地址空间从这里开始                   │
└─────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────┐
│ ★ 三个必须记住的数（它们决定了后面所有的地址）：                        │
│    0x1000     —— 加电时 PC 的值（复位向量，硬件写死的）                 │
│    0x80200000 —— 内核被放在哪（linker/qemu.ld:4 的 BASE_ADDRESS）       │
│    0x80600000 —— 内核能用到的物理内存上界（PHYSTOP）                    │
│ ★ PHYSTOP - KERNBASE = 0x400000 = 4 MB = 1024 个 4KB 页。               │
│    给了 128M 却只用 4M —— 这不是笔误，是这份代码的真实边界，            │
│    也解释了后面「为什么用户程序不能太贪心」的物理原因。                 │
└─────────────────────────────────────────────────────────────────────────┘
```

**这张表是 lab1 的地基，请务必逐行对上号。** 几条关键解释：

- `0x80000000` **起始的 2MB 是固件（OpenSBI / RUSTSBI）的地盘。**
内核**不碰**它 —— `vm.c:75` 那行给 RUSTSBI 建映射的代码是**注释掉的**。
- `0x80200000` **是内核代码起点。** 为什么是 2MB 而不是 1MB？
因为固件自己占了前 2MB，把 2MB 边界当作"安全线"。
这个数写在 `memlayout.h:102`（`KERNBASE`）和 `linker/qemu.ld:4`（`BASE_ADDRESS`）**两处**，
**必须一致**，否则内核跑飞。
- `0x80600000` **是** `PHYSTOP`（`memlayout.h:105`），物理内存上界。
注意它**不是** `0x88000000` —— 内核主动只用了 **4MB**
（`0x80600000 - 0x80200000 = 0x400000`，即 **1024 页**），剩下的 124MB 全部闲置。
**这一点后面会当作"第四处真实缺陷"来讲**（见附录 F）。
- `0x10001000` **的 virtio 磁盘**：注意它在 `0x10000000` 之上，
也就是**"设备区域"里也能有"设备套设备"**。

📖 内核镜像自己的内部结构，由链接脚本安排（`linker/qemu.ld`）：

```text
┌────────────────────────────────────────────────────────────────────────────┐
│ 段         │ 链接器给的符号    │ 内容              │ 在 lab1 里的特殊之处  │
├────────────┼───────────────────┼───────────────────┼───────────────────────┤
│ .text      │ text_start /      │ 代码 + 蹦床页     │ TRAMPOLINE            │
│            │ etext             │                   │ 映射的就是它的一部分  │
│ .rodata    │ srodata / erodata │ 只读常量          │ —                     │
│ .data      │ sdata / edata     │ 已初始化的全局变  │ —                     │
│            │                   │ 量                │                       │
│ .bss.stack │ boot_stack /      │ ★ 内核第一根栈    │ ★ 排在 sbss_clear     │
│            │ boot_stack_top    │ 32KB              │ 之前，不清零          │
│ .bss       │ sbss_clear /      │ 未初始化全局变量  │ ★ 无代码引用这两个符  │
│            │ ebss_clear        │ （proc[] 等）     │ 号                    │
└────────────────────────────────────────────────────────────────────────────┘

┌────────────────────────────────────────────────────────────────────────────┐
│ ★ 两个能自己 grep 验证的真实结论：                                         │
│    ① .bss.stack 被显式排在 sbss_clear 之前（linker/qemu.ld:45-46），       │
│       所以它不在「该清零的范围」里 —— 栈不需要初值，清了也是白清。         │
│    ② sbss_clear / ebss_clear 在全仓库【没有任何代码引用】                  │
│       （grep 结果为空）—— .bss 的零是靠 QEMU 装载 ELF 时补的。             │
│       「链接脚本写了这个符号」不等于「有人在用这个符号」，是两件事。       │
└────────────────────────────────────────────────────────────────────────────┘
```

🧠 `.bss.stack` **有个特别之处，和 lab1 直接相关**：
它排在 `sbss_clear`（`qemu.ld:46`）**之前**。也就是说，清零 `.bss` 的时候
**不会**把栈清零 —— 反正栈马上就会被用掉，清零纯属浪费。
但如果你在 gdb 里看到 `boot_stack` 里是"脏数据"，**那是正常的**。

⚠️ `ASSERT(. - _trampoline == 0x1000)`**（**`qemu.ld:22`**）** 这一行很重要：
蹦床页必须**正好一页**。多一个字节，链接就会直接报错。
这句话的存在意味着：**任何人都不能往** `trampoline.S` **里随便加代码。**


## 3. 专题二 · Sv39：39 位虚拟地址怎么切、三级页表怎么查

> 这一章是**整个 lab1 最"硬"的一章**。它讲的不是 xv6 的设计，而是
> **RISC-V 硬件规定的地址翻译规则**。规则是死的，所以这一章的结论你可以背；
> 但**推导过程必须自己走一遍**，否则后面所有的地址都会变成"魔法数字"。



### 3.1 先问：为什么要有虚拟地址？

三个理由，从弱到强：

1. **隔离**：用户程序不能碰内核的代码和数据。如果大家都在物理地址上跑，
  用户写一个 `*(int*)0x80200000 = 0` 就把内核改了。
2. **自由布局**：每个进程都可以认为"我的代码从 0 开始、栈在顶上"，
  不用关心物理内存里自己恰好被放在哪。
3. **★ 极简的共享与复用**：两个虚拟地址可以指向**同一个物理页**。
  这一条在 lab1 里马上会用到 —— `TRAMPOLINE` 在用户页表和内核页表里
   **地址相同、物理页相同**，它就是靠这个"同址映射"在换页表的瞬间活下来的。

🧠 **一句话**：虚拟地址是内核给"每一个使用者"发的**私人门牌号**，
而页表是"门牌号 → 真实的物理地址"的**翻译表**。

### 3.2 Sv39 的位段划分

RISC-V 的 Sv39 模式把 39 位虚拟地址切成四段：

```text
┌──────────────────────────────────────────────────────────────────────────┐
│ 位段        │ 位数   │ 名字             │ 作用                           │
├─────────────┼────────┼──────────────────┼────────────────────────────────┤
│ 38..30      │ 9      │ PX(2)：一级索引  │ 在根页表（512 项）里选第几项   │
│ 29..21      │ 9      │ PX(1)：二级索引  │ 在二级页表里选第几项           │
│ 20..12      │ 9      │ PX(0)：三级索引  │ 在三级页表里选第几项（★        │
│             │        │                  │ 这一项才是叶子）               │
│ 11..0       │ 12     │ 页内偏移         │ 不用查表，直接加到物理页基址上 │
│ 63..39      │ 25     │ （Sv39 不定义）  │ 必须先符号扩展成全 0 或全 1，  │
│             │        │                  │ 否则是非法地址                 │
└──────────────────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────────────────┐
│ ★ 名字你能自己推出来，就不用背：Sv39 的 39 = 9 + 9 + 9 + 12。            │
│    三个 9 位索引 × 每级 512 项，最后 12 位是页内偏移（2^12 = 4KB）。     │
│    ★ 一个常见误区：以为「一级」是最高层。xv6 的 PX(2) 才是最高层         │
│      （satp 指向的那张表），PX(0) 是最底层 —— 编号从 0 起，              │
│      但层次从 2 往下数。riscv.h:359 的 PX 公式就是这么写的。             │
└──────────────────────────────────────────────────────────────────────────┘
```

⚠️ **三个最容易记错的地方**：

1. **高 25 位（63..39）不是"没用"，是"必须符号扩展"。**
  Sv39 的合法地址必须满足：`va[63:39]` 全等于 `va[38]`。
   否则硬件直接判非法地址（page fault）。
   **这就是为什么** `MAXVA` **是** `1<<38` **而不是** `1<<39` **—— 见 3.6 节。**
2. **只有最后一段（11..0）是不用查表的。** 它是**页内偏移**，
  直接加到物理页基址上就完事。
3. **索引的方向别搞反**：`PX(2)` 是**最上层**（根页表），`PX(0)` 是**最下层**（叶子）。

📖 源码就在一行里（`kernel/include/riscv.h:357-359`）：

```c
#define PXMASK          0x1FF              /* :357  9 位掩码 */
#define PXSHIFT(level)  (PGSHIFT+(9*(level)))/* :358  每降一级少 9 位 */
#define PX(level, va) ((((uint64) (va)) >> PXSHIFT(level)) & PXMASK)  /* :359 */
```

🧠 注意 `PXSHIFT(2)` = `12 + 18` = 30、`PXSHIFT(1)` = `12 + 9` = 21、`PXSHIFT(0)` = `12`。
**"右移多少位"这件事，一个公式解决了三级。**

### 3.3 三级查表全过程

```text
┌──────────────────────────────────────────────────────────────┐
│          ① satp 寄存器里放着根页表的物理页号（PPN）          │
│        MAKE_SATP(pagetable) = SATP_SV39 | (pa >> 12)         │
└──────────────────────────────────────────────────────────────┘
                                │
                                ▼
┌──────────────────────────────────────────────────────────────┐
│ ② 拿 va 的 PX(2) 去根页表里取一项 → 得到一个 PTE             │
│    这个 PTE 指向下一级页表页的物理地址                       │
└──────────────────────────────────────────────────────────────┘
                                │
                                ▼
┌──────────────────────────────────────────────────────────────┐
│ ③ 拿 va 的 PX(1) 去二级页表里取一项 → 得到下一个 PTE         │
│    再指向三级页表页                                          │
└──────────────────────────────────────────────────────────────┘
                                │
                                ▼
┌──────────────────────────────────────────────────────────────┐
│ ④ 拿 va 的 PX(0) 去三级页表里取一项 → ★ 这次拿到的是叶子 PTE │
│    它的 PPN 就是物理页号，权限位也在这里起作用               │
└──────────────────────────────────────────────────────────────┘
                                │  软件只在建表时走同样的路
                                ▼
┌──────────────────────────────────────────────────────────────┐
│ ⑤ 物理地址 = (叶子 PTE 的 PPN << 12) + va 的低 12 位偏移     │
│    ★ 三级查表全程由【硬件】完成，速度靠 TLB 撑着             │
└──────────────────────────────────────────────────────────────┘
```

把这张图压成"三步 + 一个尾巴"：


| 步   | 用哪一段                | 在哪张表里找                 | 得到什么                      |
| --- | ------------------- | ---------------------- | ------------------------- |
| ①   | `PX(2)` = va[38:30] | **根页表**（`satp` 指向的那一页） | 下一级页表的**物理页号**            |
| ②   | `PX(1)` = va[29:21] | 二级页表                   | 下一级页表的**物理页号**            |
| ③   | `PX(0)` = va[20:12] | 三级页表                   | ★ **叶子 PTE**：最终物理页号 + 权限位 |
| 尾   | va[11:0]            | —                      | 拼到物理页号后面，得到**物理地址**       |


🧠 **每一级页表都是一整页（4096 字节），里面正好放 512 个 8 字节的 PTE。**
这就是"9 位索引"的来源：`2^9 = 512`。

⚠️ **页表项里存的是"物理页号"，不是虚拟地址，也不是"页表对象"。**
硬件只会做一件事：`物理地址 = PTE 里的 PPN << 12`，然后拿它当下一页表用。
——这个"冷冰冰"的事实，是后面理解 `PA2PTE` 的基础。

🧠 **一个必须自己算一遍的问题**：Sv39 的三级页表，能映射多大的地址空间？
每级 512 项，实际只用 512 项里的多少？

> 答：理论上 `2^39 = 512GB`。但因为高位必须符号扩展，
> **实际可用的低半区只有** `[0, 2^38)` **= 256GB**。剩下 256GB 属于"负地址区间"，
> xv6 一项都不用。**这就是** `MAXVA = 1<<38` **的真正原因。**



### 3.4 页表项的位布局

```text
┌───────────────────────────────────────────────────────────────────────────┐
│ 位段       │ 名字       │ 含义                       │ xv6 里谁用它       │
├────────────┼────────────┼────────────────────────────┼────────────────────┤
│ 53..10     │ PPN        │ 物理页号（44 位）          │ PA2PTE / PTE2PA    │
│ 9..8       │ RSW        │ 留给操作系统的两位         │ xv6 没用           │
│ 7          │ D          │ 脏页位（写过了）           │ 硬件写，xv6 不读   │
│ 6          │ A          │ 访问位（读过了）           │ 硬件写，xv6 不读   │
│ 5          │ G          │ 全局位                     │ xv6 没用           │
│ 4          │ U          │ ★ 允许 U 模式访问          │ PTE_U —— 本 lab    │
│            │            │                            │ 的核心             │
│ 3          │ X          │ 可执行                     │ PTE_X（代码段、    │
│            │            │                            │ 蹦床页）           │
│ 2          │ W          │ 可写                       │ PTE_W（数据段）    │
│ 1          │ R          │ 可读                       │ PTE_R（几乎所有映  │
│            │            │                            │ 射）               │
│ 0          │ V          │ ★ 有效位                   │ PTE_V ——           │
│            │            │                            │ 每一项都必须有它   │
└───────────────────────────────────────────────────────────────────────────┘

┌───────────────────────────────────────────────────────────────────────────┐
│ ★ 两个必须记住的位：V（这一项有没有效）和 U（U 模式能不能碰）。           │
│    内核页表的每一项都【没有】U；用户页表里用户能碰的那些才有 U。          │
│    后面「双层页表」的全部秘密就是：同一块物理页，                         │
│    在两张表里各写一个 PTE，只差一个 U 位（vm.c:274 与 :275）。            │
│    ★ PTE_FLAGS(pte) = pte & 0x3FF（riscv.h:354）—— 低 10 位就是权限位。   │
└───────────────────────────────────────────────────────────────────────────┘
```

🧠 **PTE 的低 10 位是"权限 + 状态"，高 44 位是物理页号，中间两位（RSW）留白。**
一份 PTE 恰好 64 位，和一页里的 512 项对得上。

⚠️ **本 lab 的核心是** `PTE_U`**（bit 4）。** 把这条规则刻在脑子里：

> **一个地址能不能被 U 模式访问，要看从根页表到叶子页表"整条路上"每一级 PTE 的** `U` **位。**
> 任何一级没有 `U`，这个地址对 U 模式就是不可见的。

这条规则直接解释了第 6 章 6.5 节那张"两张页表"的对照表：
**同一个物理页（**`initcode`**），在用户页表里带** `U`**、在进程内核页表里不带** `U`**。**

📖 `kernel/include/riscv.h:343-347`：

```c
#define PTE_V (1L << 0) /* valid      —— 有效位，不设就是"这一项不存在" */
#define PTE_R (1L << 1) /* 可读 */
#define PTE_W (1L << 2) /* 可写 */
#define PTE_X (1L << 3) /* 可执行 */
#define PTE_U (1L << 4) /* 1 -> user can access */
```

🧠 `PTE_V = 0` **的含义**：不是"这一项权限为 0"，而是"**这一项不存在**"。
硬件见到 `V=0` 就立刻停 —— 这是 `walk()`（`vm.c:115`）能"按需建表"的前提。

### 3.5 `PA2PTE` / `PTE2PA`：一个必须自己推的公式

```text
┌────────────────────────────────────────────────────────────────┐
│       把物理地址塞进 PTE：PA2PTE(pa) = (pa >> 12) << 10        │
│     把 PTE 还原成物理地址：PTE2PA(pte) = (pte >> 10) << 12     │
└────────────────────────────────────────────────────────────────┘
                                 │  ★ 不是随手挪的常数
                                 ▼
┌────────────────────────────────────────────────────────────────┐
│ 为什么要先 >>12 再 <<10？                                      │
│ · 物理地址的低 12 位是【页内偏移】，页表项里不需要它 —— 先丢掉 │
│ · PTE 的 PPN 从第 10 位开始 —— 再左移到该在的位置              │
│ · 一进一出，净效果等于「整体左移 2 位」，但对齐关系完全对      │
└────────────────────────────────────────────────────────────────┘
                                 │
                                 ▼
┌────────────────────────────────────────────────────────────────┐
│ 验算一下：pa = 0x80200000                                      │
│   pa >> 12        = 0x80200            （页号）                │
│   0x80200 << 10   = 0x20080000         （PPN 段）              │
│   再 | PTE_V|PTE_R|PTE_X 就得到一项合法的代码页 PTE            │
└────────────────────────────────────────────────────────────────┘
                                 │
                                 ▼
┌────────────────────────────────────────────────────────────────┐
│ ★ PTE2PA 是它的逆运算，两个函数必须严格互逆 ——                 │
│    写错任何一位，现象都是「地址翻译到一块莫名其妙的内存」，    │
│    而且往往不立刻报错，只是数据悄悄写坏。                      │
└────────────────────────────────────────────────────────────────┘
```

📖 `kernel/include/riscv.h:350-354`：

```c
#define PA2PTE(pa) ((((uint64)pa) >> 12) << 10)
#define PTE2PA(pte) (((pte) >> 10) << 12)
#define PTE_FLAGS(pte) ((pte) & 0x3FF)
```

🧠 **为什么要"先 >>12 再 <<10"？** 图上说了两句，这里再点一遍：

- `>>12`：物理地址的低 12 位是**页内偏移**，页表项里**不需要**它 —— 先丢掉；
- `<<10`：PTE 的 PPN 字段**从第 10 位开始** —— 再挪到它该在的位置。

⚠️ **这是"位运算看着像魔法，其实只有两句话"的典型。**
自己拿 `pa = 0x80200000` 算一遍：
`PA2PTE(0x80200000)` 应该等于 `0x80200000 >> 2 = 0x20080000`。
（`>>12` 得 `0x80200`，`<<10` 得 `0x80200 * 0x400 = 0x20080000`。）

🎯 **检验点 4　（位运算）**

不写代码、不用计算器，手算下面三题，然后把结果写进报告：

1. `PA2PTE(0x80200000) = ?`
2. `PTE2PA(0x20080000 | PTE_V | PTE_R | PTE_X) = ?`
3. 一个虚拟地址 `va = 0x3F10001000`，它的 `PX(2)`、`PX(1)`、`PX(0)` 各是多少？

> 答案：① `0x20080000`　② `PTE2PA` 内部先 `>>10` 把低 10 位（权限位）甩掉，
> 再 `<<12` 补回页内偏移，所以得 `0x80200000`　③ `252 / 128 / 1`
> （对照 3.7 节的索引速查表核对）。



### 3.6 `MAXVA` 为什么是 `1 << 38`

```text
┌────────────────────────────────────────────────────────────────────┐
│   MAXVA = (1L << (9 + 9 + 9 + 12 - 1)) = 1L << 38 = 0x4000000000   │
└────────────────────────────────────────────────────────────────────┘
                                   │  源码注释里写的就是这个理由
                                   ▼
┌────────────────────────────────────────────────────────────────────┐
│ 为什么是 1<<38 而不是 1<<39？                                      │
│ · Sv39 名义上能表示 2^39 个地址（39 位）                           │
│ · 但最高位那一半（bit 38 = 1）在 RISC-V 里属于【负数区间】，       │
│   必须做符号扩展才合法。                                           │
│ · xv6 干脆只用低半区：取 1<<38 当上界，省掉符号扩展的麻烦          │
└────────────────────────────────────────────────────────────────────┘
                                   │
                                   ▼
┌────────────────────────────────────────────────────────────────────┐
│ ★ 于是产生一条硬边界：任何 va >= MAXVA 的访问都是非法的，          │
│     walk() 第一件事就是 if(va >= MAXVA) panic("walk");（vm.c:118） │
│     —— 内核用一次 panic 把「地址越界」挡在源头。                   │
└────────────────────────────────────────────────────────────────────┘
```

📖 `kernel/include/riscv.h:362-365`：

```c
// MAXVA is actually one bit less than the max allowed by
// Sv39, to avoid having to sign-extend virtual addresses
// that have the high bit set.
#define MAXVA (1L << (9 + 9 + 9 + 12 - 1))     /* = 1L << 38 */
```

🧠 **源码注释已经把理由写好了**："避免那些最高位是 1 的地址需要符号扩展"。
`1<<38` 意味着：**内核只使用"低半区"，**`va[38] = 0`**，符号扩展自动满足。**
`1<<39` **就会把** `va[38]=1` **的那些地址也拉进来，它们全是"负地址"，
每一级都要额外做符号扩展检查 —— 得不偿失。**

### 3.8 TLB 与 `sfence.vma`

```text
┌───────────────────────────────────┐   ┌───────────────────────────────────┐
│            TLB 是什么             │   │         sfence.vma 解决它         │
├───────────────────────────────────┤   ├───────────────────────────────────┤
│ CPU 里缓存「va → pa」结果的小表   │   │ 刷新 TLB，让改动生效              │
│                                   │   │                                   │
│ 三级查表要访存 3 次，太慢         │   │ xv6 里出现两处：                  │
│ 所以查过的结果被记在 TLB 里       │   │ · kvminithart() vm.c:96           │
│                                   │   │   换 satp 之后立刻刷              │
│ ★ 问题来了：                      │   │ · scheduler() 换页表前后          │
│    你改了页表，                   │   │   proc.c:556 / :559               │
│    但 TLB 里还留着旧结果          │   ├───────────────────────────────────┤
│                                   │   │ ★ 少了它，现象是「改了没用」      │
└───────────────────────────────────┘   └───────────────────────────────────┘

┌───────────────────────────────────────────────────────────────────────────┐
│ ★ 「删掉 sfence.vma 会怎样」是一个很好的故障注入实验：                    │
│    程序可能跑得好好的，也可能在换页表后突然访问到旧地址 ——                │
│    因为它取决于 TLB 里当时缓存了什么。                                    │
│    这类「依赖时序的偶发错误」在操作系统里到处都是，本 lab                 │
│     只是第一次遇见。                                                      │
└───────────────────────────────────────────────────────────────────────────┘
```

🧠 **三级查表要访存 3 次，太慢**，所以 CPU 内部有一个 "地址翻译缓存" 叫 **TLB**。
它带来的后果是：**你改了页表，CPU 可能还在用旧翻译。**

📖 `kernel/include/riscv.h:328-334`：

```c
static inline void
sfence_vma()
{
  // the zero, zero means flush all TLB entries.
  // asm volatile("sfence.vma zero, zero");   ← 这一行被注释掉了
  asm volatile("sfence.vma");                 /* :333  ★ 实际用的是这一行 */
}
```

⚠️ **注意上面那个"注释掉的历史版本"**，这正是**"行号锚点必须回源码核"**的意义 ——
凭记忆写** `sfence.vma zero, zero` **看起来更"标准"，但**源码里现在跑的是** `sfence.vma`。
（这里记录一下：本指导书的早期草稿就在这一处写错了，靠**回源码逐一核对**抓了回来。）

**xv6 里有三处必须刷 TLB：**


| 位置                                  | 为什么                   |
| ----------------------------------- | --------------------- |
| `vm.c:96`（`kvminithart()` 里）        | 刚把根页表塞进 `satp`，旧翻译全作废 |
| `proc.c:556`（`scheduler()` 装载进程页表后） | 换了一张表                 |
| `proc.c:559`（切回内核页表后）               | 又换回来了                 |


⚠️ **易错点**：漏掉 `sfence_vma` 的现象是**偶发**的 ——
有时候跑得好好的，有时候访问到"上一个进程的地址"。
这就是为什么它属于"**术**"层的故障（见附录 E 第 6 条）。

### 3.9 小结与练习

**小结（四句话）**：

1. Sv39 把 39 位虚拟地址切成 **9 + 9 + 9 + 12**，只有最后 12 位不用查表。
2. **三级页表都是普通物理页**，每页 512 项 × 8 字节。查表就是三次"读内存 + 取下标"。
3. **权限位要看整条路径**，`PTE_U` 少一级都不行。
4. **改完页表必须** `sfence_vma()`，否则 TLB 里还留着旧翻译。

**练习**：

1. `MAXVA = 1L << 38`。如果改成 `1L << 39`，`TRAMPOLINE` 会变成多少？
  它还能通过"高位符号扩展"的检查吗？
   （答案：`1<<39 - 4096 = 0x7FFFFFF000`，此时 `va[38] = 1`、
   `va[63:39] = 0`，不满足符号扩展 → 非法地址。**所以必须减一位。**）
2. 一个页表只有 512 项。RISC-V 为什么不做成"一级大表"？
  （提示：一级大表要 512GB 连续内存来存页表本身。）

## 4. 专题三 · 内核的虚拟地址空间与内核页表

> 这一章回答一个问题：**内核自己也用虚拟地址，那它的虚拟地址空间长什么样？**
> 你会看到一个"反直觉"的结论：**内核把绝大多数东西放在一个非常高的地址上，
> 而它自己的代码却还在原来的低地址 —— 一模一样的地方。**



### 4.1 内核虚拟空间长什么样

```text
┌────────────────────────────────────────────────────────────────────────────┐
│ 虚拟地址      │ 这一格叫什么            │ PX2   │ 怎么来的                 │
├───────────────┼─────────────────────────┼───────┼──────────────────────────┤
│ 0x4000000000  │ MAXVA（上界，不映射）   │ 256   │ MAXVA = 1L << 38         │
│ 0x3FFFFFF000  │ TRAMPOLINE（蹦床页）    │ 255   │ MAXVA - PGSIZE           │
│ 0x3FFFFFE000  │ TRAPFRAME（陷阱帧）     │ 255   │ TRAMPOLINE - PGSIZE      │
│ 0x3F10001000  │ VIRTIO0_V               │ 252   │ VIRTIO0 + VIRT_OFFSET    │
│ 0x3F10000000  │ UART_V                  │ 252   │ UART + VIRT_OFFSET       │
│ 0x3F0C000000  │ PLIC_V                  │ 252   │ PLIC + VIRT_OFFSET       │
│ 0x3F02000000  │ CLINT_V                 │ 252   │ CLINT + VIRT_OFFSET      │
│ 0x3EC0000000  │ VKSTACK（每进程内核栈） │ 251   │ memlayout.h:114          │
│ 0x80200000    │ KERNBASE（内核代码 /    │ 2     │ == 物理地址（恒等）      │
│               │ 数据）                  │       │                          │
└────────────────────────────────────────────────────────────────────────────┘

┌────────────────────────────────────────────────────────────────────────────┐
│ ★ 这张图和物理内存布局图放在一起看，你会发现一个惊人的事实：               │
│    内核虚拟空间里【只有一小段】是低地址（KERNBASE 那 4MB），               │
│    其余全部挤在 0x3Exxxxxxxx ~ 0x3Fxxxxxxxx 这一小块「高地址区」。         │
│    为什么？因为虚拟地址的一级索引只有 0~255 可用，                         │
│    而 xv6 把设备放在 252、每进程栈放在 251，                               │
│    把「离上界最近的 255」留给蹦床（它必须在两张表里同地址）。              │
│ ★ VIRT_OFFSET = 0x3F00000000 就是把物理设备地址「抬」到高处的那个常数。    │
└────────────────────────────────────────────────────────────────────────────┘
```

🧠 **这张图第一次看会很怪**：内核虚拟空间里，"离下界最近"的部分只有
`KERNBASE`（`0x80200000`）那 4MB，其余全部挤在 `0x3Exxxxxxxx ~ 0x3Fxxxxxxxx` 这一小块。

**为什么？两个原因：**

1. **一级索引只有 0~255 可用**（因为 `MAXVA = 1<<38`，`PX(2)` 最大到 255）。
  所以你要是不想"重新编译内核的链接地址"，就只能把新东西塞进 255 那一档附近。
2. **蹦床页必须"离上界最近"**（`255,511,511`）。
  因为**它必须在用户页表和内核页表里地址完全相同** —— 只有最顶上那一页，
   两张表才有可能都"碰巧"映射到同一格。

📖 `kernel/include/memlayout.h:36` 的那个常数解释了另外半个布局：

```c
#define VIRT_OFFSET   0x3F00000000L   /* :36 */
#define UART          (…)             /* :40  QEMU 是 0x10000000 */
#define UART_V        (UART + VIRT_OFFSET)   /* :45  = 0x3F10000000 */
#define PLIC          0x0c000000L     /* :57 */
#define PLIC_V        (PLIC + VIRT_OFFSET)   /* :58  = 0x3F0C000000 */
#define CLINT         0x02000000L     /* :54 */
#define CLINT_V       (CLINT + VIRT_OFFSET)  /* :55  = 0x3F02000000 */
```

🧠 `VIRT_OFFSET` **就是把物理设备地址"抬"到高处的那个常数。**
设备厂商给的物理地址是 `0x10000000` / `0x0c000000` / `0x02000000`，
xv6 一句话把它们整体搬到 `0x3F` 开头 —— 用的是**同一个常数**，所以
**"物理地址 +** `VIRT_OFFSET` **= 虚拟地址"这条关系对所有设备都成立**。

### 4.2 恒等映射 vs 偏移映射：内核只用了两种映射

```text
┌─────────────────────────────────┐   ┌─────────────────────────────────┐
│      恒等映射（内核自己）       │   │        偏移映射（外设）         │
├─────────────────────────────────┤   ├─────────────────────────────────┤
│ 虚拟地址 == 物理地址            │   │ 虚拟地址 == 物理地址 +          │
│                                 │   │     0x3F00000000                │
│ 0x80200000 → 0x80200000         │   │                                 │
│ 0x8020xxxx → 0x8020xxxx         │   │ 0x3F10000000 → 0x10000000       │
├─────────────────────────────────┤   │ 0x3F02000000 → 0x02000000       │
│ vm.c:77  KERNBASE → KERNBASE    │   ├─────────────────────────────────┤
│ vm.c:79  etext    → etext       │   │ vm.c:31  UART_V     → UART      │
├─────────────────────────────────┤   │ vm.c:38  CLINT_V    → CLINT     │
│ ★ 好处：开分页前后              │   ├─────────────────────────────────┤
│    同一个指针照样有效           │   │ ★ 为什么要把设备挪到高处？      │
│                                 │   │    为了让「低地址」整段留给用户 │
└─────────────────────────────────┘   └─────────────────────────────────┘

┌───────────────────────────────────────────────────────────────────────┐
│ ★ 两种映射在【同一张】内核页表里并存 —— 这就是为什么看内核代码时      │
│    有时地址「看起来就是物理地址」，有时又「高得离谱」。               │
│    ★ 判断方法很简单：看头几位是不是 0x3F / 0x3E —— 是就说明它经过了   │
│     VIRT_OFFSET。                                                     │
│    ★ 反过来说：把设备放到高地址不是硬件要求，纯粹是 xv6 的设计选择。  │
└───────────────────────────────────────────────────────────────────────┘
```


| 类型       | 关系                       | 用在哪                                | 为什么                                                                   |
| -------- | ------------------------ | ---------------------------------- | --------------------------------------------------------------------- |
| **恒等映射** | `va == pa`               | 内核自己的代码 / 数据（`KERNBASE` 起 4MB）     | 编译时链接地址是物理地址；`_entry` 在没开分页时就在这个地址上跑，开了分页之后**必须还能在原地继续跑**             |
| **偏移映射** | `va == pa + VIRT_OFFSET` | 所有外设（UART / PLIC / CLINT / VIRTIO） | 内核需要"跨物理区域访问大量设备"，偏移映射让它可以**继续用** `pa + 0x3F00000000` **直接算**，不必一个个登记 |


🧠 **为什么不用"随便映射"（比如把 UART 映到** `0x1000`**）？**
因为那样内核就得记住每个设备"被搬到哪了"，而不是"加一个常数就完事"。
**xv6 的选择是"让虚拟地址成为物理地址的一个简单函数"，代价是地址看起来很难看。**
这个取舍值得记住 —— 专题七的"四条原则"里会再提一次。

⚠️ **易错点**：`KERNBASE` 是恒等映射，但**不是"整个内核都恒等"**。
`VKSTACK`（每进程内核栈）、`TRAMPOLINE`、`TRAPFRAME` 都是**高地址**。
所以你在 gdb 里看内核栈的地址，会看到 `0x3EC0000000` 附近的值 —— **那是正常的。**

### 4.3 `kvminit()` 逐行：★ 是 8 条，不是 9 条

```text
┌─────────────────────────────────────────────────────────────────────────┐
```

1. **为什么** `KERNBASE` **那两条要拆成"代码段"和"数据段"两段？**
  （答案：代码段给 `R|X` **不给** `W` —— 内核改不了自己的代码；
   数据段给 `R|W` **不给** `X` —— 数据不能被当代码执行。这是"最小权限"的直接体现。）
2. **★ 为什么这 8 条里没有一条映射** `VKSTACK`**？**
  （答案：`VKSTACK` 是**每进程**的东西，它必须在**每进程那张内核页表**里。
   见 6.6 节的 `proc_kpagetable()`。**这是个很好的扣分点。**）



### 4.4 `kvminithart()`：分页"开启"的那一瞬间

```text
┌──────────────────────────────────────────────────────────────────────┐
│                  kvminithart()（vm.c:92）只有两句话                  │
│      w_satp(MAKE_SATP(kernel_pagetable));   ← 把根页表装进 satp      │
│          sfence_vma();                          ← 刷新 TLB           │
└──────────────────────────────────────────────────────────────────────┘
                                    │  顺序不能反
                                    ▼
┌──────────────────────────────────────────────────────────────────────┐
│ ★ 这一瞬间发生了三件事：                                             │
│ ① satp 的 MODE 字段变成 8（Sv39），分页【开启】；                    │
│ ② 从此以后 CPU 发出的每一个地址都要先查页表；                        │
│ ③ 之所以现在才开，是因为——页表必须先建好，否则第一条指令就查表失败。 │
└──────────────────────────────────────────────────────────────────────┘
                                    │
                                    ▼
┌──────────────────────────────────────────────────────────────────────┐
│ ★ 为什么 `kvminit` 里可以一路用物理地址？                            │
│    因为分页还没开，CPU 把地址直接当物理地址用。                      │
│    ★ 为什么 kvminit 之后还要 sfence.vma()？                          │
│    因为 TLB 里可能还留着旧的翻译结果，不刷新会读到「上一套世界」。   │
└──────────────────────────────────────────────────────────────────────┘
```

📖 全文只有两句（`kernel/vm.c:92-100`）：

```c
void
kvminithart()
{
  w_satp(MAKE_SATP(kernel_pagetable));   /* :94  把根页表装进 satp */
  sfence_vma();                          /* :96  刷新 TLB */
}
```

🧠 **这两句的顺序不能反**：先换表，再刷缓存。
反过来的话，你刷掉的是**旧表**留下的缓存，新表装上去之后缓存又是空的 ——
虽然"看起来也能跑"，但语义是错的。

**这一瞬间，CPU 眼里"地址"的含义永久地改变了。** 具体说：


|                  | 之前                   | 之后                                  |
| ---------------- | -------------------- | ----------------------------------- |
| 你写的 `0x80200000` | 就是物理地址 0x80200000    | 要被 `satp` 里的表翻译一次（结果恰好还是它自己，因为恒等映射） |
| 非法地址             | 想访问就访问               | 会触发 **page fault**                  |
| `printf` 里的串口地址  | 用的是物理地址 `0x10000000` | 内核代码里写的是 `UART_V`，翻译成 `0x10000000`  |


⚠️ **注意一个细节**：`kvminithart()` 之后，`main()` 里剩下的初始化代码
**依然在** `0x8020xxxx` **这个物理地址上执行** —— 因为恒等映射保证
"虚拟地址 = 物理地址"。**这就是为什么第 6 条映射必须是恒等的：不恒等，内核会在打开的瞬间失联。**

### 4.5 虚拟地址 → 物理地址：两个具体例子

```text
┌─────────────────────────────────────────────────────────┐
│ 例 1：内核访问自己的代码 —— va = 0x80200000（恒等映射） │
└─────────────────────────────────────────────────────────┘
                             │  这就是「恒等」的由来
                             ▼
┌─────────────────────────────────────────────────────────┐
│ PX(2) = 2　→ 根页表第 2 项 → 二级页表 A                 │
│ PX(1) = 1　→ A 的第 1 项     → 三级页表 B               │
│ PX(0) = 0　→ B 的第 0 项     → ★ 叶子 PTE               │
│ 叶子 PTE 的 PPN = 0x80200，偏移 = 0x000                 │
│ → 物理地址 = 0x80200000　（和虚拟地址一模一样）         │
└─────────────────────────────────────────────────────────┘
                             │
                             ▼
┌─────────────────────────────────────────────────────────┐
│  例 2：内核访问跳板 —— va = 0x3FFFFFF000（TRAMPOLINE）  │
└─────────────────────────────────────────────────────────┘
                             │  ★ 三级索引全是最大值
                             ▼
┌─────────────────────────────────────────────────────────┐
│ PX(2) = 255 → 根页表第 255 项                           │
│ PX(1) = 511 → 二级第 511 项                             │
│ PX(0) = 511 → 三级第 511 项 → ★ 叶子 PTE                │
│ 叶子 PTE 的 PPN 指向 trampoline 那个物理页              │
│ → 物理地址 = trampoline 的物理地址（≠ 虚拟地址）        │
└─────────────────────────────────────────────────────────┘
```

**例 1：内核访问自己的代码 ——** `va = 0x80200000`**（恒等映射）**


| 步   | 用哪段      | 值       | 查到                                           |
| --- | -------- | ------- | -------------------------------------------- |
| ①   | `PX(2)`  | 2       | 根页表第 2 项 → 二级页表 A 的物理地址                      |
| ②   | `PX(1)`  | 1       | A 的第 1 项 → 三级页表 B 的物理地址                      |
| ③   | `PX(0)`  | 0       | B 的第 0 项 → ★ **叶子 PTE**                      |
| 尾   | va[11:0] | `0x000` | 叶子 PTE 的 `PPN = 0x80200`，拼上偏移 → `0x80200000` |


**结论**：`va == pa`。这就是"恒等"的由来。

**例 2：内核访问串口 ——** `va = 0x3F10000000`**（偏移映射）**


| 步   | 用哪段      | 值       | 查到                               |
| --- | -------- | ------- | -------------------------------- |
| ①   | `PX(2)`  | 252     | 根页表第 252 项（`kvminit():31` 建的那一项） |
| ②   | `PX(1)`  | 128     | 二级页表第 128 项                      |
| ③   | `PX(0)`  | 0       | 叶子 PTE，`PPN = 0x10000`           |
| 尾   | va[11:0] | `0x000` | 拼出 → `0x10000000`                |


**结论**：`pa = va - 0x3F00000000`。这就是"偏移"的由来。

### 4.6 硬件 walk 与软件 walk 的区别

```text
┌───────────────────────────────────┐   ┌───────────────────────────────────┐
│   硬件（MMU）：每次访存都走一遍   │   │      软件（vm.c:115 walk）：      │
├───────────────────────────────────┤   │     只在建表时走                  │
│ ① 读 satp 拿根页表物理地址        │   ├───────────────────────────────────┤
│ ② 取 PX(2) 项，检查 PTE_V         │   │ ① 从 level = 2 递减到 1           │
│ ③ 取 PX(1) 项，检查 PTE_V         │   │ ② 每层读 PTE                      │
│ ④ 取 PX(0) 项，检查 PTE_V 与权限  │   │ ③ 若 PTE_V 为 0 且 alloc != 0     │
│ ⑤ 拼出物理地址，完成访存          │   │    → kalloc 一页、清零、写回 PTE  │
├───────────────────────────────────┤   │ ④ 返回【最底层那一项的地址】      │
│ ★ 任何一步失败 → 页错误           │   ├───────────────────────────────────┤
│    scause = 12 / 13 / 15          │   │ ★ 返回的是 pte_t*，不是物理地址   │
│                                   │   │    调用者自己往里写 PA2PTE(pa)|   │
│                                   │   │     perm                          │
└───────────────────────────────────┘   └───────────────────────────────────┘

┌───────────────────────────────────────────────────────────────────────────┐
│ ★ 两套「走法」必须一致，否则页面全是乱的：                                │
│    硬件的规定写在 RISC-V 手册里，软件的实现在 vm.c:115-133。              │
│    ★ walk 的返回值是一根【指针】，指向那个 PTE 在页表页里的位置 ——        │
│      所以 mappages 拿到它之后可以直接 *pte = PA2PTE(pa) | perm | PTE_V。  │
│    ★ walk 还会 panic 掉 va >= MAXVA 的情况，把非法地址挡在建表阶段。      │
└───────────────────────────────────────────────────────────────────────────┘
```

🧠 **这是两个完全不同的** `walk`**，名字一样但角色不同：**


|       | 硬件（MMU）       | 软件（`vm.c:115` 的 `walk()`）              |
| ----- | ------------- | -------------------------------------- |
| 什么时候跑 | **每一次访存**     | 只在**建表**时                              |
| 目标    | 把 va 翻译成 pa   | 找到（或新建）**那一项 PTE 的地址**                 |
| 会不会分配 | 不会            | `alloc != 0` 时**会** `kalloc` **一页并清零** |
| 失败怎么办 | 触发 page fault | 返回 0                                   |


📖 `vm.c:115` 的签名一眼看出它的用途：

```c
pte_t *
walk(pagetable_t pagetable, uint64 va, int alloc)
```

⚠️ **注意它返回的是** `pte_t`***（一个指针），不是物理地址。**
所以 `mappages()` 才能这样写：`*pte = PA2PTE(pa) | perm | PTE_V;` ——
**拿到那一格的地址，然后往里写。**

🧠 **"软件 walk 会 kalloc" 这件事很关键**：
它意味着**页表是"按需长出来的"**。你第一次访问一个新地址区域时，
中间几级页表页可能还不存在，`walk` 会顺手把它们建好。
**这就是为什么** `kvminit()` **里不需要"预先为每一级分配页表"** —— 那是 `mappages` 自己会处理的事。

### 4.7 小结与练习

**小结（四句话）**：

1. 内核虚拟空间是"**一头一尾**"：低处是恒等映射的 `KERNBASE`，
  高处是偏移映射的设备 + 蹦床 + 每进程栈。
2. `kvminit()` 在 QEMU 平台建 **8 条**映射，其中**没有一条**管 `VKSTACK`。
3. `kvminithart()` 的两句话**顺序不能反**；它之后，"地址"这个词的含义永久改变。
4. **硬件 walk 每次访存都跑；软件 walk 只在建表时跑，还会顺手 kalloc。**

**练习**：

1. 把 `kvminithart()` 里的 `sfence_vma()` 注释掉，会怎样？
  （答案：多数情况下还能跑 —— 因为此刻 TLB 里几乎没有有效翻译。
   **这是一个"看起来像假通、其实是真隐患"的例子**，见附录 E 第 6 条。）
2. 如果把第 1 条 `kvmmap(UART_V, UART, PGSIZE, PTE_R | PTE_W)` 的 size 改成 `0x100`，
  `printf` 会怎样？（答案：只有前 256 字节能用，串口寄存器有偏移超出时会 page fault。
   **注意：**`printf` **在** `kvminithart()` **之前就已经能用了**，
   所以你要看到的现象可能出现在 `kvminit()` 之后的某个打印上。）

### 5.2 两个 hart 的分工

```text
┌───────────────────────────────────┐   ┌───────────────────────────────────┐
│ 第 0 号 hart（第一个到 main 的）  │   │       第 1 号及以后的 hart        │

│ 用 CAS 抢一个「我是第一个」的标记 │   │ 看到标记已经不是 0，走 else 分支  │
│ if (__sync_bool_compare_and_swap( │   │ while (started != 1) 原地等       │
│     &started, 0, -1))             │   ├───────────────────────────────────┤
├───────────────────────────────────┤   │ 醒来后只做三件事：                │
│ 做全部 15 件初始化的事            │   │ · kvminithart()   装自己的 satp   │
│                                   │   │ · trapinithart()  装自己的 trap   │
│ 然后用 sbi_send_ipi 把其它 hart   │   │     向量                          │
│     叫醒                          │   │ · plicinithart()  使能自己的中断  │
│ 最后 started = 1 放行             │   │                                   │

┌───────────────────────────────────────────────────────────────────────────┐
│ ★ 关键洞察：所有初始化只做一遍，但「与 hart 有关的寄存器」每个 hart       │
│     各设一次。                                                            │
│    satp / stvec / sie 都是每 hart 一份的硬件状态 —— 不是全局变量。        │
│    ★ 这就是为什么 main() 要写两段：第一段是「建世界」，第二段是「入籍」。 │
│    最后两颗 hart 都掉进同一个 scheduler()（main.c:83），开始抢进程跑。    │
└───────────────────────────────────────────────────────────────────────────┘
```

📖 `:36` 那一行是"抢第一"的关键：

```c
if (__sync_bool_compare_and_swap(&started, 0, -1))
```

🧠 `__sync_bool_compare_and_swap(&started, 0, -1)` **在做什么？**
它读 `started`，**如果等于 0 就原子地改成** `-1` **并返回真**；
否则返回假。**两个 hart 同时执行这一行，只有一个能成功。**
失败的 hart 走 `else`（`:70`），在 `while (started != 1)` 上转圈。

⚠️ **为什么不能两个 hart 都做初始化？**
因为它们会**抢同一个物理页**（比如 `kernel_pagetable = kalloc()`）——
两个核拿到两块不同的根页表，各自往自己的表里建映射，
最后两个核看到的地址空间**不一样**。这是最隐蔽的一类 bug。

🧠 **为什么** `started = 1`**（**`:68`**）要放在** `sbi_send_ipi` **之后？**
因为其他 hart 在等这个标志。标志一旦为 1，它们立刻开始 `kvminithart()`。
而 `kvminithart()` 要读 `kernel_pagetable` —— **如果根页表还没建完就放闸，它们会读到半个表。**
`:67` 的 `__sync_synchronize()` 是编译屏障，防止编译器把 `started = 1` 提前。

🧠 **依赖链里最硬的三条：**

1. `consoleinit` **→ 一切 printf**。所以它第一。
2. `kinit` **→** `kvminit` **→** `kvminithart`。
  没有物理页分配器就建不了页表；没有页表就开不了分页。
3. `kvminithart` **→ 之后所有初始化**。
  因为一旦开了分页，所有地址都要过页表；
   **如果页表建得有遗漏，后面的代码在访问某个地址时会直接 page fault。**

⚠️ **一条很容易被忽略的依赖**：`trapinithart()`（`:47`）必须在 `userinit()`（`:58`）**之前**。
因为 `userinit()` 造出来的进程是 `RUNNABLE` 的，
一旦 `scheduler()` 把它挑走，它就会**从用户态执行** `ecall`，
而 `ecall` 需要 `stvec` 指向蹦床 —— 那时 `stvec` 必须已经装好。

### 5.5 小结与练习

**小结（四句话）**：

1. `main()` 里 QEMU 平台有 **15 个**初始化调用（`main.c:37` ~ `:58`），不是十二三个。
2. `consoleinit()` **永远第一**（它是观测手段），`kvminithart()` **是一道分水岭**。
3. **只有 0 号 hart 做全部初始化**，其他 hart 等闸门、然后各装各的 `satp` / `stvec` / PLIC。
4. `userinit()` **是最后一步**，它造出第一个进程；然后 `scheduler()` 接管，
  **永不返回。**

**练习**：

1. 把 `printfinit()` 挪到 `kinit()` 之后，有什么风险？
  （答案：`kinit()` 里的 `printf("kernel_end: %p, phystop: %p")`（`kalloc.c:37`）
   会在 `pr.lock` 未初始化时被调用 → 多 hart 下可能把两行输出搅在一起。）
2. `main.c:72-73` 的 `while (started != 1) ;` 是**忙等**。为什么这里可以用忙等？
  （答案：此时其他 hart 还在初始化阶段，没有其他进程可跑，"让出 CPU" 没有意义。
   **但注意** `:66` **之后，等的那一方是在** `intr_on()` **之前忙等的** ——
   如果 `sbi_send_ipi` 没生效，这里会永久挂死。）

## 6. 专题五 · 内核怎么造出第一个用户进程

> 这一章回答一个问题：**"进程"这个东西，是内核怎么变出来的？**
> 你会看到它其实只有 **7 步**，核心只有一句话：
> **"分配三页（陷阱帧 / 用户页表 / 内核页表）+ 一页装 52 字节的机器码 + 把状态改成 RUNNABLE"。**



### 6.1 从一个问题出发

**进程是怎么"生"出来的？** 先破除两个误解：

- ✗ "进程 = 一段程序"：不对。**同一段程序可以有好几个进程**（各跑各的一份）。
- ✗ "内核提供了 `create_process()` 系统调用"：不对。
**第一个进程不是"被创建"的，是内核对**自己**调的** `userinit()`**。**

🧠 **一句话**：内核里 `proc[]` 是一张**固定大小的槽位表**（`NPROC` 个），
"造一个进程"= **找一个** `UNUSED` **的槽，填满它，把它标成** `RUNNABLE`。
就这么朴素。

### 6.2 `userinit()` 的七步

📖 **源码（**`kernel/proc.c:283-311`**），逐行对号：**

```c
void
userinit(void)
{
  struct proc *p;
  p = allocproc();                                       /* :289  ① 找槽位 + 分配资源 */
  initproc = p;                                          /* :290  ② 记下"1 号进程" */
  uvminit(p->pagetable, p->kpagetable,
          initcode, sizeof(initcode));                    /* :294  ③ 给两张表建 va=0 的映射 */
  p->sz = PGSIZE;                                        /* :295  ④ 进程大小 = 1 页 */
  p->trapframe->epc = 0x0;      /* user program counter *//* :298  ⑤ 从 0 开始执行 */
  p->trapframe->sp  = PGSIZE;   /* user stack pointer   *//* :299  ⑥ 栈在页顶 */
  safestrcpy(p->name, "initcode", sizeof(p->name));       /* :301  起个名字 */
  p->state = RUNNABLE;                                   /* :303  ⑦ ★ 可以跑了 */
  p->tmask = 0;                                          /* :305  trace 默认关 */
  release(&p->lock);                                     /* :307 */
}
```

🧠 `allocproc()` **里到底分配了什么？**（`proc.c:127` 起，这是"资源账单"）


| 行          | 分配什么                                                  | 大小          | 谁用                    |
| ---------- | ----------------------------------------------------- | ----------- | --------------------- |
| `:142`     | `allocpid()` —— 分配 pid                                | —           | 内核记账                  |
| `:145`     | **trapframe 一页**（`kalloc`）                            | 4KB         | `trampoline.S` 存用户寄存器 |
| `:152`     | **用户页表**（`proc_pagetable`）                            | 4KB + 下层表页  | U 模式用                 |
| `:153`     | **进程内核页表**（`proc_kpagetable`）                         | 4KB + 下层表页  | S 模式用                 |
| `:159`     | `p->kstack = VKSTACK`                                 | ★ 不分配，只是记地址 | 内核栈（物理页在 `:570` 分）    |
| `:164-165` | 设 `context.ra = forkret`、`context.sp = kstack+PGSIZE` | —           | 第一次被调度时从 `forkret` 开始 |


⚠️ `p->kstack = VKSTACK`**（**`:159`**）这一行很容易误读**：
它只是把**虚拟地址** `0x3EC0000000` 记下来，
**真正的物理页是在** `proc_kpagetable()` **里** `kalloc` **的**（`vm.c:570`）。
**所以你看到** `kstack` **是个高地址、而物理页在别处 —— 那是正常的。**

### 6.3 `initcode`：52 字节的机器码

```text
┌────────────────────────────────────────────────────────────────────────────┐
│ 偏移   │ 机器码（十六进制）    │ 反汇编             │ 它在干什么           │
├────────┼───────────────────────┼────────────────────┼──────────────────────┤
│ 0x00   │ 17 05 00 00           │ auipc a0, 0x0      │ a0 = 当前 PC         │
│ 0x04   │ 13 05 45 02           │ addi  a0, a0, 0x24 │ a0 → "/init" 的地址  │
│ 0x08   │ 97 05 00 00           │ auipc a1, 0x0      │ a1 = 当前 PC         │
│ 0x0c   │ 93 85 35 02           │ addi  a1, a1, 0x23 │ a1 → argv 的地址     │
│ 0x10   │ 93 08 70 00           │ li    a7, 7        │ ★ a7 = SYS_exec      │
│ 0x14   │ 73 00 00 00           │ ecall              │ ★ 第一次从用户态进内 │
│        │                       │                    │ 核                   │
│ 0x18   │ 93 08 20 00           │ li    a7, 2        │ a7 = SYS_exit        │
│ 0x1c   │ 73 00 00 00           │ ecall              │ exec 万一失败就退场  │
│ 0x20   │ ef f0 9f ff           │ jal   ra, -8       │ 退回上一条 ecall，   │
│        │                       │                    │ 死循环               │
│ 0x24   │ 2f 69 6e 69 74 00 00  │ "/init" + NUL      │ 要执行的程序路径     │
│ 0x2b   │ 24 00 00 00           │ .long init         │ argv[0]，值 0x24     │
│ 0x2f   │ 00 00 00 00           │ .long 0            │ argv[1] = NULL       │
│ 0x33   │ 00                    │ （收尾）           │ 补到 52 字节         │
└────────────────────────────────────────────────────────────────────────────┘

┌────────────────────────────────────────────────────────────────────────────┐
│ ★ 数一数：整个数组是 **52 字节**（0x00 ~ 0x33），不是「56」。              │
│    52 = 9 条指令 × 4 + 字符串 7 字节 + argv 8 字节 + 1 字节收尾。          │
│ ★ 两个关键偏移只能从 la 展开的 addi 立即数读出来，别凭对齐猜：             │
│    init = 0x00 + 0x24 = 0x24　　argv = 0x08 + 0x23 = 0x2b                  │
│ ★ 为什么第一个用户程序不是编译出来的？                                     │
│    因为编译它需要一个文件系统、一个可执行文件格式、一个 shell……            │
│    而这些东西【一个都还不存在】。所以它是手写的机器码，                    │
│    用最小的代价把世界启动起来 —— 启动自举的经典手法。                      │

```

📖 `kernel/proc.c:241-249`**：**

```c

  0x17, 0x05, 0x00, 0x00, 0x13, 0x05, 0x45, 0x02,
  0x97, 0x05, 0x00, 0x00, 0x93, 0x85, 0x35, 0x02,
  0x93, 0x08, 0x70, 0x00, 0x73, 0x00, 0x00, 0x00,
```

⚠️ **它是 52 字节，不是 56。** 自己数：前 6 行每行 8 个 = 48，最后一行 4 个 → **52**。
**（这就是"自报数字必须能复核"的一个实例。）**

🧠 **这 52 个字节是"三种东西拼在一起"的（★ 逐字节对，别凭印象）：**


| 偏移            | 内容                                 | 是什么                                       |
| ------------- | ---------------------------------- | ----------------------------------------- |
| `0x00 ~ 0x23` | 9 条指令（36 字节）                       | 汇编好的**可执行代码**                             |
| `0x24 ~ 0x2a` | `2f 69 6e 69 74 00 00`             | 字符串 `/init` 加 NUL（`.string` 自己还会再补一个 NUL） |
| `0x2b ~ 0x2e` | `24 00 00 00`                      | `argv[0]` = `0x24`（指向字符串）                 |
| `0x2f ~ 0x32` | `00 00 00 00`                      | `argv[1]` = NULL                          |
| `0x33`        | `00`                               | 收尾填充                                      |
| **合计**        | **52 字节（**`0x00` **~** `0x33`**）** |                                           |


📖 对照源码 `xv6-user/initcode.S`（28 行）：

```asm
        la a0, init           /* :9   a0 = "/init" 的地址（= 0x24） */
        la a1, argv           /* :10  a1 = argv 的地址（= 0x2b） */
        li a7, SYS_exec       /* :11  ★ a7 = 7 */
        ecall                 /* :12  ★ 第一次从用户态进内核 */
exit:
        li a7, SYS_exit       /* :16  万一 exec 返回了 */
        ecall                 /* :17 */
        jal exit              /* :18  死循环 */
init:
  .string "/init\0"           /* :22 */
        .p2align 2
argv:
  .long init                  /* :27 */
  .long 0                     /* :28 */
```

🧠 `init` **和** `argv` **各是几？—— 只能从** `la` **展开出的立即数读出来：**


| 指令                   | 在哪个 PC | 展开成                                 | 算出来                           |
| -------------------- | ------ | ----------------------------------- | ----------------------------- |
| `la a0, init`（`:9`）  | `0x00` | `auipc a0, 0` + `addi a0, a0, 0x24` | `init = 0x00 + 0x24 =` `0x24` |
| `la a1, argv`（`:10`） | `0x08` | `auipc a1, 0` + `addi a1, a1, 0x23` | `argv = 0x08 + 0x23 =` `0x2b` |


⚠️⚠️ **注意** `argv = 0x2b`**，不是** `0x2c`**！**
大多数人会想"字符串 6 字节 → 补到 4 字节对齐 → 应该在 `0x2c`"，
**但机器码里的立即数是** `0x23`**，算出来就是** `0x2b`**。**
**这是本指导书里"凭推理会猜错、必须回源码读"的最典型一处。**
（`argv[0]` 这个 `.long` 里存的值，正是 `init` 的地址 —— 也就是 `0x24`。）

🎯 **检验点 8　（initcode）**

1. `initcode` **一共多少字节？为什么不是 56？**
2. `initcode[0x24]` **那个字节是什么？**`argv[0]` **又在哪个偏移？**
3. **这段代码执行的第一条指令是哪个？它执行完之后 a0 是多少？**

> 答案：① 52 字节；② `initcode[0x24] = 0x2f`，正是 `/` 的 ASCII ——
> 也就是字符串 `/init` 的起点；`argv[0]` 在 `0x2b`（存的值是 `0x24`）；
> ③ `la a0, init`（展开成 `auipc` + `addi`），执行完 `a0 = 0x24`。

🧠 **注意第 2 问的陷阱**：不少人会答 "`argv[0]` 在 `0x2c`"
（理由听着很顺："字符串 7 字节 + 补到 4 字节对齐"），**但真值是** `0x2b`。
**这就是"凡是能从源码/机器码读出来的数，一律现场读"的具体价值。**

```text
┌────────────────────────────────────────────────────────────────┐
```

📖 **这是全 lab1 最值得反复读的 15 行代码（**`kernel/vm.c:265-280`**）：**

```c
void
uvminit(pagetable_t pagetable, pagetable_t kpagetable, uchar *src, uint sz)
{
  char *mem;
  if(sz >= PGSIZE) panic("inituvm: more than a page");   /* :269 */
  mem = kalloc();                                        /* :271  ① 买一页物理内存 */
  memset(mem, 0, PGSIZE);                                /* :273  ② 清零 */
  mappages(pagetable,  0, PGSIZE, (uint64)mem, PTE_W|PTE_R|PTE_X|PTE_U); /* :274 ③a 带 U */
  mappages(kpagetable, 0, PGSIZE, (uint64)mem, PTE_W|PTE_R|PTE_X);       /* :275 ③b 不带 U */
  memmove(mem, src, sz);                                 /* :276  ④ 把 52 字节拷进去 */
}
```

⚠️ `sz >= PGSIZE` **就 panic（**`:269`**）** —— 这是"一个进程的初始代码不能超过一页"的硬限制。
`initcode` 只有 52 字节，所以没事；**但这也是为什么真正的** `init` **必须立刻** `exec("/init")` ——
一页装不下一个完整的用户程序。

🧠 **★** `:274` **和** `:275` **这两行的唯一差别就是有没有** `PTE_U`**。**
**这是整份指导书里最重要的两行。** 一句话解释：

> **同一个物理页** `mem`**，被两张不同的页表映射到同一个虚拟地址 0，
> 但一个"允许用户访问"、一个"不允许"。**
> 内核按需要切换 `satp` 来决定"现在拿哪张表看世界"。

**这就是"双层页表"这个名字的由来。**

### 6.5 两张页表的对照

```text
┌───────────────────────────────┐   ┌───────────────────────────────┐
│   p->pagetable（用户页表）    │   │ p->kpagetable（进程内核页表） │
├───────────────────────────────┤   ├───────────────────────────────┤
│ who: U 模式用                 │   │ who: S 模式用                 │
│ satp: 用户态时装载            │   │ satp: scheduler 装载          │
├───────────────────────────────┤   │       proc.c:555              │
│ 装了：                        │   ├───────────────────────────────┤
│ · 0 → initcode 物理页         │   │ 装了：                        │
│   ★ 带 PTE_U                  │   │ · 0 → initcode 物理页         │
│ · TRAMPOLINE（无 U）          │   │   ★ 不带 PTE_U                │
│ · TRAPFRAME（无 U）           │   │ · 内核的 8 条映射（浅拷贝）   │
├───────────────────────────────┤   │ · VKSTACK（本进程内核栈）     │
│ ★ 看不到内核代码、            │   ├───────────────────────────────┤
│    看不到外设                 │   │ ★ 从内核里能直接读写用户内存  │
└───────────────────────────────┘   └───────────────────────────────┘

┌───────────────────────────────────────────────────────────────────┐
│ ★ 为什么要两张表，而不是一张表加切换？                            │
│    因为页表是【每进程】的资源，而内核代码是【全局】的。           │
│    proc_kpagetable 用「浅拷贝根页表」把全局内核映射继承过来，     │
│    再单独补上「本进程的内核栈」—— 这样切换进程时只换根页表一项，  │
│    内核代码那部分（三级页表页）完全共享，省内存又省时间。         │
└───────────────────────────────────────────────────────────────────┘
```


|               | `p->pagetable`（用户页表）                          | `p->kpagetable`（进程内核页表）          |
| ------------- | --------------------------------------------- | -------------------------------- |
| 谁在用           | **U 模式**（用户程序）                                | **S 模式**（这个进程进内核之后）              |
| 什么时候装进 `satp` | `usertrapret()` 的最后（`trap.c:137` → `userret`） | `scheduler()` 挑中它时（`proc.c:555`） |
| `va = 0` 那条   | 指向 `initcode` 物理页，**带** `PTE_U`               | 指向**同一个**物理页，**不带** `PTE_U`      |
| `TRAMPOLINE`  | `proc.c:212`，`PTE_R                           | PTE_X`，**无 U**                   |
| `TRAPFRAME`   | `proc.c:219`，`PTE_R                           | PTE_W`，**无 U**                   |
| 内核代码          | **没有**                                        | 有（`0x80200000` 恒等那 4MB）          |


🧠 **一个必须想清楚的问题：为什么** `TRAMPOLINE` **和** `TRAPFRAME` **不给** `PTE_U`**？**

> 因为它们是**内核的代码和数据**。用户页表里之所以要映射它们，
> 是因为**蹦床页要在"换页表的瞬间"还能被取到指令**，
> 但**用户程序绝不能直接跳进去执行或读改陷阱帧**。
> **"映射"和"允许用户访问"是两件事** —— 这正是 `PTE_U` 存在的意义。

⚠️ **易错点**：进程**有两张页表**这件事，是 xv6-k210 相对标准 xv6 的一个特色
（标准 xv6 里内核全局共用一张表，每个进程只有一张用户表）；
这里为了支持 `VKSTACK` 让每进程有自己的内核栈，才引入 `kpagetable`。
**如果你的报告只写"一张页表"，那是把两种 xv6 搞混了。**

### 6.6 `proc_kpagetable()`：每进程内核页表

```text
┌─────────────────────────────────────────────────────────────────────────┐
│                  proc_kpagetable()　vm.c:562　只有四步                  │
└─────────────────────────────────────────────────────────────────────────┘
                                     │
                                     ▼
┌─────────────────────────────────────────────────────────────────────────┐
│ ① kpt = kalloc()　vm.c:564 —— 分配一页放根页表                          │
└─────────────────────────────────────────────────────────────────────────┘
                                     │  第 1 级（根）拷贝，下面各级共享
                                     ▼
┌─────────────────────────────────────────────────────────────────────────┐
│ ② memmove(kpt, kernel_pagetable, PGSIZE)　vm.c:567                      │
│    ★★ 只复制【一页】= 512 个 PTE = 根页表整整一层                       │
└─────────────────────────────────────────────────────────────────────────┘
                                     │  ★ 必须单独映射，不能共享
                                     ▼
┌─────────────────────────────────────────────────────────────────────────┐
│ ③ pstack = kalloc()　vm.c:570                                           │
│    mappages(kpt, VKSTACK, PGSIZE, pstack, PTE_R|PTE_W)　vm.c:573        │
│    ★ 注释原文：remap stack and trampoline, because they share           │
│      the same page table of level 1 and 0                               │
└─────────────────────────────────────────────────────────────────────────┘
                                     │
                                     ▼
┌─────────────────────────────────────────────────────────────────────────┐
│ ④ 返回 kpt                                                              │
└─────────────────────────────────────────────────────────────────────────┘
                                     │
                                     ▼
┌─────────────────────────────────────────────────────────────────────────┐
│ ★ 为什么只复制 4096 字节就够？                                          │
│    因为内核的地址只用了根页表里极少几个下标（2、251、252、255…），      │
│    把这一层拷过来，就等于把「内核的全部映射」继承了过来，               │
│    ★ 而下面两级页表页是【共享】的 —— 改一处内核映射，所有进程同时生效。 │
│ ★ 代价：VKSTACK / TRAMPOLINE 落在同一层根项下，必须逐进程重映射。       │
└─────────────────────────────────────────────────────────────────────────┘
```

📖 **全文 20 行（**`kernel/vm.c:561-581`**）：**

```c
pagetable_t
proc_kpagetable()
{
  pagetable_t kpt = (pagetable_t) kalloc();      /* :564  ① 一页放根页表 */
  if (kpt == NULL) return NULL;
  memmove(kpt, kernel_pagetable, PGSIZE);        /* :567  ② ★ 把全局内核页表根整页拷过来 */

  char *pstack = kalloc();                       /* :570  ③ 内核栈的物理页 */
  if (pstack == NULL) goto fail;
  if (mappages(kpt, VKSTACK, PGSIZE,
               (uint64)pstack, PTE_R | PTE_W) != 0)   /* :573  ④ 在 VKSTACK 建映射 */
    goto fail;
  return kpt;
fail:
  kvmfree(kpt, 1);
  return NULL;
}
```

🧠 `memmove` **一页 = "浅拷贝根页表"。**
这一步拷贝的是**根页表那 512 个 PTE**，所以新表**共享**下面所有各级页表 ——
**只有** `VKSTACK` **那一条是新建的**（因为每个进程要自己的栈）。

⚠️ **注意** `:573` **的权限是** `PTE_R | PTE_W`**，没有** `PTE_X`**。**
内核栈不需要执行 —— **又是"最小权限"。**

🤖 **AI 追问点 6**

> 请 AI 解释：`proc_kpagetable()` **里** `memmove` **只拷一页，
> 是不是意味着"进程 A 和进程 B 的内核页表共用同一批下层页表页"？
> 如果 A 改了自己内核页表里的某个映射，B 会受影响吗？**
> 正确答案要点：**根页表那一页是各自独立的**，但下面各级页表页是共享的；
> 因为**建立新映射这件事在内核启动之后几乎不再发生**（只有 `VKSTACK` 那一处），
> 所以这个"浅拷贝"是安全的。
> **如果它能说清"为什么这里可以偷懒"，说明它真懂了。**

🧠 **用户地址空间其实很"空"**：`0` 到 `p->sz`；然后是**天大的空洞**；
再往上三格是 `TRAMPOLINE` 和 `TRAPFRAME`。

📖 三处关键定义：

```c
#define MAXUVA    RUSTSBI_BASE        /* memlayout.h:127  = 0x80000000，用户地址上界 */
#define TRAMPOLINE (MAXVA - PGSIZE)   /* memlayout.h:109 */
#define TRAPFRAME  (TRAMPOLINE - PGSIZE) /* memlayout.h:125 */
```

**为什么用户地址上界是** `0x80000000`**？**
因为那正是**物理 RAM 的起点**（`RUSTSBI_BASE`）。
—— 这么设计不是为了别的，**就是为了让"用户虚拟地址"永远不会直接等于"某个物理地址"**，
从而杜绝"用户猜一个物理地址就能读到内核"的可能。**这是一个纯策略性的选择。**

⚠️ `MAXUVA` **是"上界"，不是"用户能用 2GB"**：
用户实际能用的只有 `[0, p->sz)`，`p->sz` 从 `PGSIZE` 开始，
靠 `sbrk()` 往上长。**中间那一大段全是"未映射"的洞。**

### 6.8 三层关系：页表 ↔ 虚拟空间 ↔ 物理空间

```text
┌────────────────────┐   ┌────────────────────┐   ┌────────────────────┐
│    用户虚拟空间    │   │    内核虚拟空间    │   │      物理内存      │
├────────────────────┤   ├────────────────────┤   ├────────────────────┤
│ 0 → initcode       │   │ 0x80200000 恒等    │   │ initcode 物理页    │
│ p->sz 以内         │   │ 0x3EC0000000 栈    │   │ trampoline 物理页  │
│ TRAMPOLINE         │   │ 0x3F1xxxxxxx 设备  │   │ trapframe 物理页   │
│ TRAPFRAME          │   │ TRAMPOLINE（同址） │   │ 内核代码 / 数据    │
│                    │   │                    │   │ 4MB RAM            │
└────────────────────┘   └────────────────────┘   └────────────────────┘

┌──────────────────────────────────────────────────────────────────────┐
│ ★ 三列之间的关系，用一句话说清：                                     │
│    两张页表把同一个物理页映射到各自的虚拟地址上。                    │
│    · initcode 那一页：用户表里 va=0 带 U，内核表里 va=0 不带 U；     │
│    · trampoline 那一页：两张表里都是 TRAMPOLINE（同址，无 U）；      │
│    · 内核代码那一页：只在（每进程的）内核表里有，用户表里没有。      │
│    ★ 判据：一张页表里有没有某一项，决定「那个模式能不能看见它」。    │
└──────────────────────────────────────────────────────────────────────┘
```

这张图把 lab1 的空间概念收束成三列。**看它的正确姿势是"从左到右连线"**：

1. **左边（用户虚拟空间）的** `0 → initcode` —— 连到中间的 `TRAMPOLINE` 附近？不，是连到右边那页物理内存。
2. **中间（内核虚拟空间）的** `0x3EC0000000 栈` —— 连到右边另一页物理内存。
3. `TRAMPOLINE` **在左中两列"地址相同"** —— 连到**同一页**物理内存。★ 这是蹦床能工作的全部秘密。

🧠 **一句话总结三层关系**：

> **页表是"翻译器"，虚拟空间是"翻译的结果"，物理空间是"被翻译的东西"。**
> 一张页表定义了一个虚拟空间；两个虚拟空间只要指向同一页物理内存，就能共享数据。
> `TRAMPOLINE` **就是"让两个虚拟空间在同一格交汇"这一技巧的产物。**

```text
│ 168          │ a7                       │ ★ 系统调用号就藏在这里        │
```

📖 `struct trapframe` 一共 **288 字节**（`trap.h:17-54`），**正好塞进一页没问题**：


| 偏移           | 字段                            | 谁写 / 谁读                                                  |
| ------------ | ----------------------------- | -------------------------------------------------------- |
| `0`          | `kernel_satp`                 | `usertrapret():118` 写；`trampoline` 读                     |
| `8`          | `kernel_sp`                   | `usertrapret():119` 写（= `kstack + PGSIZE`）               |
| `16`         | `kernel_trap`                 | `usertrapret():120` 写（= `usertrap` 的地址）                  |
| `24`         | `epc`                         | ★ `usertrap():66` 存 `sepc`；`usertrapret():133` 写回 `sepc` |
| `32`         | `kernel_hartid`               | `usertrapret():121` 写                                    |
| `40` ~ `280` | `ra` / `sp` / `gp` / … / `t6` | ★ `trampoline.S` 逐条存取                                    |


🧠 **为什么** `trapframe` **要单独一页，而不是塞进** `struct proc`**？**
因为 `trampoline.S` 需要**一个固定的、不依赖当前栈的地址**来存寄存器，
而这个地址必须在**用户页表里也存在**（`TRAPFRAME`），
且**用户不能碰**（无 `PTE_U`）。
—— 三个约束一起，就只能是"单独一页 + 无 U + 两表同址"。

📖 **蹦床页的两半（**`kernel/trampoline.S`**，147 行）**：


|       | `uservec`（`:16` 起）                                                                 | `userret`（`:90` 起）                    |
| ----- | ---------------------------------------------------------------------------------- | ------------------------------------- |
| 方向    | U → S                                                                              | S → U                                 |
| 第一件事  | `csrrw a0, sscratch, a0`（`:29`，换出 `TRAPFRAME` 地址）                                  | `csrw satp, a1`（`:100`，换用户页表）         |
| 中间    | 存 31 个寄存器 → 装 `sp` / `tp` / `trap` / `satp` → `csrw satp` → `sfence.vma` → `jr t0` | 恢复 31 个寄存器 → `csrrw a0, sscratch, a0` |
| 最后一件事 | `jr t0`（`:87`，跳到 `usertrap`，**不返回**）                                               | `sret`（`:147`，回用户态）                   |


⚠️ `sscratch` **的作用要理解**：陷入瞬间，`a0` 里是用户的值，
但你要用一个寄存器去指 `TRAPFRAME` —— 所以先 `csrrw a0, sscratch, a0`
把 `a0` 和 `sscratch` **对调**，这样 `a0` 就成了 `TRAPFRAME`，
而用户的 `a0` 安全地暂存在 `sscratch` 里，等会儿再换回来（`:143`）。
**这一手"对调"是整段蹦床代码里最漂亮的地方。**

📖 `sbi_shutdown()` **从哪来（**`kernel/include/sbi.h`**）：**

```c
#define SBI_SHUTDOWN 8                                   /* :19 */
#define SBI_CALL(which, arg0, arg1, arg2, arg3) ({ ... })  /* :21  一段内联汇编 */
#define SBI_CALL_0(which) SBI_CALL(which, 0, 0, 0, 0)      /* :35 */

static inline void sbi_shutdown(void)                      /* :58 */
{
  SBI_CALL_0(SBI_SHUTDOWN);                                /* :60 */
}
```

🧠 `SBI_CALL_0(SBI_SHUTDOWN)` **最终做了什么？**
它把 `SBI_SHUTDOWN`（= 8）放进 `a7`，然后执行 `ecall`。
**和** `usys.pl` **的桩几乎一模一样** —— 区别只在"往哪去"：

- 用户态的 `ecall` → 进 S 模式（`stvec` 指向 `uservec`）；
- S 模式的 `ecall` → 进 M 模式（`mtvec` 指向 OpenSBI 自己的入口）。

**"用同一条指令，跨两级特权"** —— 这是 RISC-V 设计上很优雅的一点。

⚠️ `sbi_shutdown()` **之后为什么还要** `return 0;`**？**
因为 C 函数必须有返回值，编译器不管"这个函数会不会返回"。
**这行** `return 0` **永远不会被执行到** —— 但如果关机**失败**（比如 `SBI_SHUTDOWN` 没被支持），执行流会回到 `halt.c:11` 那句"报警器" printf。
（注意：`halt()` 声明为 `noreturn` 且开了 `-O`，这句 printf 在最终目标文件里**可能已被优化删除**——看不到它不等于没走到；可靠的判据始终是"QEMU 退没退出"。）
**所以那句话的真正身份是"没生效的报警器"，不是"bug 提示"。**

### 7.4 两次 `ecall` 对照

```text
┌──────────────────────────────────┐   ┌──────────────────────────────────┐
│   第一条 ecall（用户程序发的）   │   │     第二条 ecall（内核发的）     │
├──────────────────────────────────┤   ├──────────────────────────────────┤
│ 谁执行：用户态桩 usys.S          │   │ 谁执行：sbi_shutdown()           │
│ 方向：U → S                      │   │ 方向：S → M                      │
│ a7：★ 27（SYS_halt）             │   │ a7：★ 8（SBI_SHUTDOWN）          │
│ 去哪：TRAMPOLINE + uservec       │   │ 去哪：固件自己的 trap 入口       │
│ 谁接：usertrap（trap.c:51）      │   │ 谁接：OpenSBI 的 M 模式代码      │
│ 回来吗：会（sret）               │   │ 回来吗：★ 永不返回               │
├──────────────────────────────────┤   ├──────────────────────────────────┤
│ ★ 请求「内核帮我办事」           │   │ ★ 请求「固件帮我断电」           │
└──────────────────────────────────┘   └──────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────┐
│ ★ 一个高频误解：以为 ecall 是「直接跳到内核」。                         │
│    它只是「发起一次环境调用」——去哪由【当前特权级】和【stvec / mtvec】  │
│     决定。                                                              │
│    U 模式 ecall 去 S 的 stvec；S 模式 ecall 去 M 的 mtvec。             │
│    ★ 同一个指令助记符 ecall，在两个特权级下目的地完全不同 ——            │
│      这正是「权限委托」得以实现的关键：每一级只能向上一级求助。         │
└─────────────────────────────────────────────────────────────────────────┘
```


|         | 第一次 `ecall`               | 第二次 `ecall`                  |
| ------- | ------------------------- | ---------------------------- |
| 谁执行     | 用户态桩（`usys.S`）            | `sbi_shutdown()`（`sbi.h:60`） |
| 方向      | **U → S**                 | **S → M**                    |
| `a7`    | **27**（`SYS_halt`）        | **8**（`SBI_SHUTDOWN`）        |
| 去哪      | `TRAMPOLINE + uservec`    | 固件自己的 M 模式入口                 |
| 谁接      | `usertrap()`（`trap.c:51`） | OpenSBI                      |
| **回来吗** | **会**（正常时经 `sret` 回用户态）   | **永不返回**                     |


🧠 **一个很值得琢磨的问题**：既然最终是固件关的电，
为什么不让用户程序**直接**发一次 `ecall` 到 M 模式？

> 因为 **U 模式的** `ecall` **只能到 S 模式**（硬件规定，`ecall` 在哪个模式执行，
> 就陷入"下一个更高的模式"）。U 模式永远碰不到 M 模式的服务。
> **于是必须"绕一圈"：U → S（内核），S → M（固件）。**
> 这一圈不是性能损失，**而是"隔离"的代价 —— 也正是它存在的意义。**
> 内核在这一圈里做了两件事：**验证请求合法**（`syscall()` 的边界检查）、
> **决定要不要答应**（比如未来可以加"只有 root 能关机"的策略）。



### 7.5 那条"看起来莫名其妙"的 `epc += 4`

```text
┌─────────────────────────────────────────────────────────────────┐
│ 一条看起来莫名其妙的语句：p->trapframe->epc += 4　（trap.c:74） │
└─────────────────────────────────────────────────────────────────┘
                                 │  这就是「+4」的全部理由
                                 ▼
┌─────────────────────────────────────────────────────────────────┐
│ 不加会怎样？                                                    │
│ · 硬件设置 sepc 时，指向的是【那条 ecall 指令自己的地址】       │
│ · usertrap 把 sepc 存进 trapframe->epc，一路原样带回用户态      │
│ · sret 于是跳回 ecall 那条指令 → 又陷入 → 又来一次 +4 …         │
│ ★ 现象：死循环，用户程序一步也走不动                            │
└─────────────────────────────────────────────────────────────────┘
                                 │
                                 ▼
┌─────────────────────────────────────────────────────────────────┐
│ 为什么是 4？                                                    │
│ · RISC-V 指令定长 4 字节（无压缩指令时）                        │
│ · +4 正好是下一条指令                                           │
└─────────────────────────────────────────────────────────────────┘
                                 │  两条路径的差异是有原因的
                                 ▼
┌─────────────────────────────────────────────────────────────────┐
│ ★ 顺便看一眼：另一条 trap 路径没有这个 +4                       │
│    kerneltrap（trap.c:149）处理的是内核态异常，                 │
│    它恢复 sepc 用的是「进入时的原值」（trap.c:151 / :177）——    │
│    因为内核态没有「ecall 之后要跳过它」这件事。                 │
└─────────────────────────────────────────────────────────────────┘
```

📖 `kernel/trap.c:66-74`：

```c
  p->trapframe->epc = r_sepc();          /* :66  把硬件存的 sepc 搬到 trapframe */

  if(r_scause() == 8){                   /* :68  8 = ecall from U mode */
    if(p->killed) exit(-1);
    // sepc points to the ecall instruction,
    // but we want to return to the next instruction.
    p->trapframe->epc += 4;              /* :74  ★ 加 4 */
    intr_on();
    syscall();                           /* :78 */
  }
```

🧠 **为什么是 +4？**

- 硬件在陷入时，把 `sepc` 设成**那条** `ecall` **指令自己的地址**（不是下一条）。
- 系统调用"办完事"之后，我们期望回到 `ecall` **的下一条**继续跑。
- RISC-V 指令长度是 4 字节（本课程不用压缩指令） → **下一条 = 当前 + 4**。

⚠️ **不加会怎样？（这就是附录 E 第 5 条）**
`sret` 会跳回**那条** `ecall` **指令** → 又一次陷入 → 又一次 `+4`（但 `epc` 是刚存的、
又是 ecall 的地址）→ **用户程序一步也走不动，屏幕上什么都不打印。**
**这是"死循环"级别的问题，而且非常安静** —— 没有报错，就是不前进。

🧠 **为什么不在硬件里直接 +4？**
因为**不是所有** `ecall` **都想"继续下一条"** ——
内核可以故意不 +4，让 `sret` 回到原地，从而**"重试"这次系统调用**
（比如 `sbrk` 空间不够时，等一会儿再来一次）。**把决定权留给软件，是刻意的设计。**

### 7.6 `stvec` 为什么要设两次

```text
┌──────────────────────────────────┐   ┌──────────────────────────────────┐
│    启动时设一次（内核态入口）    │   │ 每次返回用户态前再设一次（用户态 │
├──────────────────────────────────┤   │     入口）                       │
│ trapinithart()　trap.c:36        │   ├──────────────────────────────────┤
│ w_stvec((uint64)kernelvec)       │   │ usertrapret()　trap.c:114        │
├──────────────────────────────────┤   │ w_stvec(TRAMPOLINE + (uservec -  │
│ 用途：内核自己出异常 / 中断时    │   │     trampoline))                 │
│      从哪里进去                  │   ├──────────────────────────────────┤
│                                  │   │ 用途：下一次用户态陷入时         │
│ ★ 此时还没有用户进程，           │   │      从蹦床页进去                │
│    所以只需要内核入口            │   │                                  │
│                                  │   │ ★ 而 usertrap() 一进门又把它     │
│                                  │   │    改回 kernelvec（trap.c:61）   │
└──────────────────────────────────┘   └──────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────┐
│ ★ 规律：stvec 永远指向「下一个可能发生的 trap 该去哪」。                │
│    在用户态跑 → 指向蹦床（因为下一跳是用户发起的）；                    │
│    在内核里跑 → 指向 kernelvec。                                        │
│    ★ 所以 usertrap 进门第一件事就是改回 kernelvec（trap.c:61）——        │
│      因为从现在起 CPU 在内核里，后面的中断必须走内核那条路。            │
└─────────────────────────────────────────────────────────────────────────┘
```


|          | 什么时候设                         | 设成什么                                  | 用途                    |
| -------- | ----------------------------- | ------------------------------------- | --------------------- |
| 第一次      | `trapinithart()`（`trap.c:36`） | `kernelvec`                           | **内核自己**出异常 / 中断时从哪进去 |
| （又设回内核态） | `usertrap()`（`trap.c:61`）     | `kernelvec`                           | 进内核之后就改回来             |
| 第二次      | `usertrapret()`（`trap.c:114`） | `TRAMPOLINE + (uservec - trampoline)` | **下一次用户态陷入**从蹦床页进去    |


🧠 **一句话解释**：`stvec` 是"**当前这张特权级的地图上，出事了往哪跑**"。
内核态需要 `kernelvec`（它跑在内核栈上），
用户态需要蹦床（它得先换栈、换页表）。**两个入口，一个寄存器，所以来回换。**

⚠️ **易错点**：`usertrap()` 里 `:61` 那一次"改成 kernelvec"很容易被忽略，
但**它是必须的** —— 否则在内核里发生一次中断（比如时钟），
`stvec` 还指着蹦床页，`uservec` 会去读 `sscratch`，
而此刻 `sscratch` 里并不是 `TRAPFRAME` → **直接跑飞。**

### 7.7 RISC-V 的三种特权态

```text
┌────────────────────────────────────────────────────────────────────────────┐
│ 特权级 │ 全名 / 别名         │ 谁能用             │ 它管什么               │
├────────┼─────────────────────┼────────────────────┼────────────────────────┤
│ M      │ Machine（机器模式） │ 固件 OpenSBI /     │ ★ 最高权：所有 CSR、   │
│        │                     │ RUSTSBI            │ PMP、电源 / 复位、     │
│        │                     │                    │ 时钟源                 │
│ S      │ Supervisor（监管模  │ ★ xv6 内核         │ 页表（satp）、         │
│        │ 式）                │                    │ 陷阱（stvec/sepc/scaus │
│        │                     │                    │ e）、中断使能          │
│ U      │ User（用户模式）    │ ★ 用户程序         │ 只能跑自己的指令、     │
│        │                     │                    │ 碰自己的内存；★        │
│        │                     │                    │ 一条特权指令都没有     │
└────────────────────────────────────────────────────────────────────────────┘

┌────────────────────────────────────────────────────────────────────────────┐
│ ★ 三级的设计原则：能力逐级上收，权限逐级下放。                             │
│    · U 连「关机」这种指令都发不出来 —— 它只能 ecall 求人；                 │
│    · S 能管内存和中断，但改不了时钟源、发不了复位信号；                    │
│    · M 什么都能干，但它平时不管事，只提供「服务」。                        │
│ ★ 于是 halt 这一条链路天然要跨两次级 —— 这不是麻烦，这是设计。             │
│    ★ 顺带说清另一件事：特权级 != 页表。                                    │
│      U 模式和 S 模式都会用 satp，只是用的是不同的那张表。                  │
└────────────────────────────────────────────────────────────────────────────┘
```

🧠 **一句话记住三者的分工：**


| 特权级   | 别名         | 谁住在这                  | 它能管什么                                           |
| ----- | ---------- | --------------------- | ----------------------------------------------- |
| **M** | Machine    | 固件（OpenSBI / RUSTSBI） | ★ 最高权：所有 CSR、PMP、**电源 / 复位**、时钟源                |
| **S** | Supervisor | xv6 内核                | 页表（`satp`）、陷阱（`stvec` / `sepc` / `scause`）、中断使能 |
| **U** | User       | 用户程序                  | 只能跑自己的指令、读自己的数据                                 |


🧠 **"特权"这个词到底在保护什么？**
它保护的是**"谁能改规则"**：

- 用户改不了 `satp` → 改不了"地址翻译规则"；
- 内核改不了 `mtvec` / 改不了电源 → 改不了"最高规则"。

**"规则"和"用规则做事"分给不同级别** —— 这就是整个操作系统安全的基石。

### 7.9 三种特权态转换的关键指令

```text
┌────────────────────────────────────────────────────────────────────────────┐
│ 指令       │ 方向        │ 硬件做了什么               │ xv6 里谁用         │
├────────────┼─────────────┼────────────────────────────┼────────────────────┤
│ ecall      │ 升级（求助  │ 保存 PC 到 sepc，设        │ usys.S 的桩、      │
│            │ ）          │ scause，跳 stvec / mtvec   │ sbi.h 的封装       │
│ sret       │ 降级（返回  │ 按 sstatus.SPP 决定回 U    │ trampoline.S:147（ │
│            │ ）          │ 还是 S，PC ← sepc          │ 回用户态）         │
│ mret       │ 降级（固件  │ M 模式返回，语义与 sret    │ ★ 固件内部，       │
│            │ 返回）      │ 类似但方向更高             │ 内核看不到         │
│ sfence.vma │ 不是换特权  │ 刷新 TLB 里的地址翻译缓存  │ kvminithart :96、  │
│            │ 级          │                            │ scheduler          │
│            │             │                            │ :556/:559          │
└────────────────────────────────────────────────────────────────────────────┘

┌────────────────────────────────────────────────────────────────────────────┐
│ ★ 三条换特权级的指令，方向是「ecall 往上、sret/mret 往下」：               │
│    你只能【请求】更高一级帮忙，永远不能【直接跳】过去。                    │
│    ★ 这条规则由硬件保证：U 模式执行 sret 会直接触发非法指令异常。          │
│    ★ sfence.vma 常被误当成特权指令 —— 它不是；它只是清缓存，               │
│      但它出现的时机（换完 satp 之后）很重要。                              │
└────────────────────────────────────────────────────────────────────────────┘
```

📖 **本 lab 里你会遇到四种"跨界"指令，一次分清：**


| 指令           | 方向           | 硬件做什么                                        | xv6 里谁用                                                 |
| ------------ | ------------ | -------------------------------------------- | ------------------------------------------------------- |
| `ecall`      | **升级**（求助）   | 存 PC → `sepc`；设 `scause`；跳 `stvec` / `mtvec` | `usys.S` 的桩、`sbi.h` 的封装                                 |
| `sret`       | **降级**（返回）   | 按 `sstatus.SPP` 决定回 U 还是 S；PC ← `sepc`       | `trampoline.S:147`（回用户态）                                |
| `mret`       | **降级**（固件返回） | M 模式返回，语义类似但方向更高                             | ★ 固件内部，内核看不到                                            |
| `sfence.vma` | 不换特权         | 刷新 TLB                                       | `kvminithart():96`、`scheduler():556/:559`、蹦床 `:81/:103` |


🧠 **RISC-V 只有** `ecall` **一条"主动升级"指令**（外加各种异常/中断是被动升级），
**降级永远靠** `sret` **/** `mret`**。**
这种"**升级只有一条路，降级各回各家**"的对称性，是 RISC-V 陷阱设计的一大特色 ——
比某些架构"用同一条指令软中断"要清楚得多。

🤖 **AI 追问点 7**

> 请 AI 回答：`usertrap()` **里为什么不把** `ecall` **那条指令的** `epc` **改成"下一条"，
> 而是留在原地，让** `usertrapret()` **去写** `sepc`**？**
> 再问它：**"如果我想实现一个'系统调用重试'语义（比如** `EAGAIN`**），
> 应该怎么用** `epc`**？"**
> 正确答案要点：`epc` 在 `trapframe` 里就是一个普通的字段，
> 内核可以**随意改写**它；`usertrapret():133` 会把 `trapframe->epc` 写进 `sepc`。
> **所以"改不改** `+4`**、改多少"完全是软件的自由** ——
> 这就是"决策权在内核"的具体体现。



### 7.10 小结与练习

**小结（四句话）**：

1. `halt` 走的是"**两次** `ecall`"：`U → S`（用户请示内核） + `S → M`（内核请示固件）。
2. **你要写的只有一行** `sbi_shutdown();` —— 但你要能讲清为什么"必须绕这一圈"。
3. `epc += 4`**（**`trap.c:74`**）是"不 +4 就死循环"的关键**；
  `stvec` 设两次、`satp` 换两次，都是"两条指令之间不能跳"逼出来的。
4. **三种特权态的本质是"谁有权改规则"**，而不是"谁能做什么事"。

**练习**：

1. 把 `trap.c:74` 的 `epc += 4` 注释掉，跑一次看现象。
  （应该看到：系统起来后敲 `halt` 毫无反应，屏幕静止。
   **这就是附录 E 第 5 条，属于"术"层故障。**）
2. 把 `sys_halt` 写成 `return -1;`（现在的样子），敲 `halt`：
  现象是 QEMU 不退出、也没有打印（报警 printf 被优化掉了）。
  **再把 `halt.c` 里那句 printf 删掉、跑一遍**，对比两次的现象差在哪。
3. **开放题**：如果内核想加一条"只有 pid = 1 的进程才能关机"的策略，
  应该加在哪一层？为什么不是加在 `sbi_shutdown()` 里？
   （提示：`sbi_shutdown()` 是 M 模式的**能力**，不是**策略**。
   策略属于内核 —— 这就是专题七的"机制与策略分离"。）

```text
│    ★ 但深度是分层的：基础要求只到「器 + 技」，进阶要求加「术」，           │
│      最高要求把「法 + 道」说清楚。                                         │
│    ★ 判断自己到没到「术」层，用一个问题：                                  │
│      「如果把 epc += 4 删掉，现象是什么，为什么？」答得出来就过了。        │
└────────────────────────────────────────────────────────────────────────────┘
```

🧠 **"道法术技器"是五个提问角度，不是五个难度层级。**
你可以同时站在五个角度问同一个东西：


| 层     | 它回答什么问题    | 在 `halt` 这条链路上                     | 怎么算"立住了"                       |
| ----- | ---------- | ---------------------------------- | ------------------------------ |
| **器** | 用什么工具 / 机器 | `ecall` 指令、`syscalls[]` 表、gdb、make | 改完 `xv6-user/` 知道要重跑 `make fs` |
| **技** | 机制怎么串起来    | 号 → 桩 → 声明 → 分发表 → 实现 → 名字表        | 能说全要改几处，漏一处知道报什么               |
| **术** | 机制为什么这么设计  | 两次 `ecall`、双层页表、`+4`、`stvec` 两次    | 能画出链路图并解释每一步                   |
| **法** | 规则 / 架构    | 四处一致性、机制与策略分离                      | 能说"加新 syscall 该按什么规矩走"         |
| **道** | 设计哲学       | 特权隔离、"请求"而不是"命令"                   | 能说出"为什么用户不能直接关机"               |


⚠️ **最容易犯的错误是"停在技层"** —— 把代码改对、现象对，就算完事。
但 lab1 的验收里，"技"只值一半分。**"为什么"才是这个实验的主菜。**

### 8.2 两条路径：从上到下 / 从下到上

```text
┌──────────────────────────────────┐   ┌──────────────────────────────────┐
```

🧠 **这两条路径对应两种真实工作状态，你都要会：**

**路径 A（从上到下，设计师视角）**：从"为什么要特权隔离"出发，一路推到代码。
这条路走顺了，你就能**设计**一个新的系统调用。

**路径 B（从下到上，侦探视角）**：从"屏幕上的一个现象"出发，一路倒推回代码。
这条路走顺了，你就能**调试**。

**合起来看，你会发现一件很漂亮的事**：
**A 路的每一步，在 B 路里都有一个对应的"现象指纹"。**


| A 路（设计）                     | B 路（诊断）                 | 现象指纹                |
| --------------------------- | ----------------------- | ------------------- |
| 要"请求" → 要 `ecall`           | 完全没有输出、程序不动             | ★ `epc` 没 `+4`（死循环） |
| 要"分发" → 要 `syscalls[]`      | `unknown sys call 27`   | 分发表缺项               |
| 要"记名字" → 要 `sysnames[]`     | `strace 134217728 halt` 后乱码/(null) | 名字表缺项（**潜伏**）       |
| 要"真关机" → 要 `sbi_shutdown()` | 敲 `halt` 后 QEMU 不退出   | 实现是空壳（报警 printf 常被优化掉） |


**这张表建议背下来。** 验收口试时，老师极可能从"现象"提问，让你倒着走一遍。

### 8.3 四条设计原则

```text
┌────────────────────────────────────────────────────────────────────────────┐
│ 原则         │ 一句话                   │ 在 halt 里的体现                 │
├──────────────┼──────────────────────────┼──────────────────────────────────┤
│ 特权隔离     │ 不同信任级别的东西不能混 │ 用户页表里没有内核代码；         │
│              │ 在一张表里               │ TRAMPOLINE 无 PTE_U              │
│ 机制与策略分 │ 内核提供「能做」，       │ syscall() 一张表分发，           │
│ 离           │ 用户决定「做什么」       │ 加号不用改分发代码               │
│ 最小权限     │ 能用多少给多少，         │ 设备映射只给 R|W 不给 X；        │
│              │ 不多给一位               │ 内核映射里没有 U                 │
│ 不可逆操作要 │ 关机、复位这类动作必须走 │ 两次 ecall：U→S 请示，S→M 请示   │
│ 请示         │ 「请求」通道             │                                  │
└────────────────────────────────────────────────────────────────────────────┘

┌────────────────────────────────────────────────────────────────────────────┐
│ ★ 四条原则里，「机制与策略分离」最容易被当成空话 —— 用代码验一下：         │
│    syscall() 函数体（syscall.c:205-222）里【没有任何一个具体的 syscall     │
│     名字】，                                                               │
│    它只做三件事：读 a7、按号查表、把结果写回 a0。                          │
│    所以加 SYS_halt 一行都不用改它 —— 这就是分离的好处。                    │
│    ★ 而 sysnames[] 那张表是个反面例子：它和 syscalls[] 必须成对维护，      │
│      漏了就埋下一颗越界读的雷（见专题八的 CP③ 任务 2）。                   │
└────────────────────────────────────────────────────────────────────────────┘
```

**逐条落到** `halt` **上：**

1. **特权隔离**：
  用户页表里**没有内核代码**；`TRAMPOLINE` 和 `TRAPFRAME` **无** `PTE_U`；
   用户改不了 `satp`。
   → **结果**：用户程序无法"跳过内核"去碰硬件。
2. **机制与策略分离**：
  `syscall()` 是一张表分发，"加号不用改分发代码"。
   `sbi_shutdown()` 提供"能关机"这个**机制**；
   "谁能关机"这个**策略**留在内核。
   → **结果**：加一个新系统调用，**不用动内核的调度、陷阱、分发逻辑**。
3. **最小权限**：
  设备映射只给 `R|W` **不给** `X`（`vm.c:31/:35/:38/:41/:42`）；
   内核代码段给 `R|X` **不给** `W`（`vm.c:77`）；
   内核数据段给 `R|W` **不给** `X`（`vm.c:79`）；
   内核栈给 `R|W` **不给** `X`（`vm.c:573`）；
   `TRAMPOLINE` 无 `U`、`TRAPFRAME` 无 `U`。
   → **结果**：任何一处被攻破，能造成的破坏都被限制在那一格里。
4. **不可逆操作必须走完整流程**：
  关机、复位这类动作，**必须** `U → S → M` 两次请示。
   → **结果**：任何一层都能拒绝、都能记录、都能加审计。

🧠 **这四条不是"课本上的大词"，它们在这份代码里有具体的行号。**
**验收时要求你"指出行号"的地方，就是这里。**

🤖 **AI 追问点 8**

> 请 AI 把"最小权限"这一条**在** `kvminit()` **的 8 条映射里逐条对一遍**，
> 说出每一条分别体现了什么权限约束。
> 然后追问：**"如果我把** `:79` **那条数据段映射改成** `PTE_R | PTE_W | PTE_X`**，

📖 越界读发生在这里（`syscall.c:211-221`）：


📖 **还有一个"第 8 处"但已经给你了**：`xv6-user/user.h:36` 的
`void halt(void) __attribute__((noreturn));` —— 用户程序的**函数声明**。
**加新 syscall 时你也要在这里加一行**，否则 `xxx.c` 里的调用会报"隐式声明"。

⚠️ **注意** `usys.pl` **里的顺序和** `sysnum.h` **里的顺序不一样**：
学生版 `usys.pl` 的 `entry("rename")` 在 `:43`，
而 `sysnum.h` 里 `SYS_rename` 是 26。**顺序不影响正确性**（有名字对应），
但**看的时候容易串行**，要小心。

🧠 **为什么加一个 syscall 要改 7 处，而不止 1 处？**
因为**这是一条跨了"用户态 → 内核态"边界的接口**：
用户侧需要一个函数名（②⑧），内核侧需要一个编号（①）、一个声明（③）、
一张分发（④）表、一张名字表（⑤）和一个实现（⑥），
再加上一个能跑的程序（⑦）。
**"接口"从来不是一处的代码，而是一组必须一致的约定。**

🚨 **形态 F：一个"反向"的陷阱，必须单独讲**

`xv6-user/user.h:36` 把 `halt` 声明成了：

```c
void halt(void) __attribute__((noreturn));
```

`__attribute__((noreturn))` 是**告诉编译器"这个函数不会返回"**。
在 `-O` 优化档下（`Makefile:76` 的 `CFLAGS` 里有 `-O`），
编译器**有权把** `halt.c:11` **那句** `printf("should not reach here")` **整个删掉**。

⚠️ **后果是：你的 CP④ 没做完，屏幕上也可能"什么都没打印"。**
如果你按"没看到 `should not reach here` 就是修好了"来判断，
**你会把形态 A 误判成通过。**

🎯 **所以 lab1 有一条铁律：唯一不可伪造的判据是"QEMU 进程真的退出了"。**


| 现象                                     | 含义                      |
| -------------------------------------- | ----------------------- |
| 屏幕回到 **xv6 的** `-> / $` **提示符**             | 没修好（halt 返回了，shell 继续跑） |
| 屏幕回到**你自己的 shell 提示符**（`make run` 结束了） | ✅ 真关机了                  |

### B.1 CP①　`kernel/include/sysnum.h`

**学生版** `:59` **是占位** `#define SYS_halt 0`**。你要把它改成 27，并交解释。**

参考实现：

```c
#define SYS_halt   27  // CP①: 新增 SYS_halt，号 27（1~26 已占满，顺延）
```

**三个问题：**

- **为什么不能是 0？** → `syscall.c:211` 的条件是 `num > 0`，**0 会被当成非法**，
现象是 `unknown sys call 0`。
- **为什么不能是 100？** → 这个数会成为 `syscalls[]` 的下标。
`NELEM(syscalls)` = 最大指定下标 + 1，会一下变成 101，
**中间 73 个格子是空指针** —— 只要有人调 28 ~ 99 里任何一个，就是 `NULL` 解引用。
- **为什么必须"连续且不冲突"？** → 撞号意味着同一格被指定初始化器写两次：
GCC 会报 `initialized field overwritten`，或者后者静默覆盖前者 ——
**两种都很难查。**

**为什么一个"教学实验"里会有缺陷？**

### F.1 第一处：指导书要求跑 `make qemu-gdb`，但原 Makefile 里没有这个目标

- **现象**：`make: *** No rule to make target 'qemu-gdb'`。
- **本质**：「**文档要求的东西，代码里必须真的有**」——
这是"文档与代码一致性"的一个活标本。
- **本课程的处理**：v3 版已经在**两版 Makefile** 里补齐了
`qemu-gdb:`（`:163`）和 `gdb:`（`:169`），与 lab2 的 Makefile **逐行同构**。
- **你要学的**：看到"照文档做却报错"时，**先怀疑文档，再怀疑自己** ——
然后用 `grep` 去源码里确认。



### F.2 第二处：`sysnames[]` 比 `syscalls[]` 容易漏（★ 设计出来的潜伏隐患）

- **现象**：功能**完全正常**；只有 `strace 134217728 halt` 之后才乱码 / 崩。
- **本质**：`sysnames[]` 的用途只有一处（`syscall.c:214-216` 的 trace 分支），
而 `p->tmask` 默认是 0（`proc.c:305`）——
**"平时不走的代码路径"是最好的藏身处。**
- **触发方式**：在 shell 里敲 `strace 134217728 halt`（134217728 = 1<<27）。
- **你要学的**：**改一处要连带检查几处**。
`sysnum.h`(号) / `usys.pl`(桩) / `syscall.c`(extern + `syscalls`) / `sysproc.c`(实现)
是**四处一致性**；`sysnames[]` 是**容易被忽略的第五处**。



### F.3 第三处：两个 syscall 的实现写在 `syscall.c` 里

- **现象**：能编译、能跑、结果全对。
- **本质**：`kernel/syscall.c` 的 `:224` 有 `sys_test_proc()`、
`:232` 有 `sys_sysinfo()` —— **本该在** `sysproc.c` **里的实现，跑到了分发表所在的文件里。**
- **为什么不好**：`syscall.c` 的职责是"**分发**"，
不是"**实现**"。层次混了之后，别人找实现要去两个地方。
- **你要学的**：**"能跑"和"干净"是两件事。**
实验室里能跑就行，工程里不行。**但注意：本实验不要求你改它** ——
因为改它会让两版代码差异变大，违背"差异最小化"的原则。



### F.4 第四处：`PHYSTOP` 只到 `0x80600000`，128MB 的机器只用了 4MB

- **现象**：什么都没有 —— **没有任何断言会报错。**
- **本质**：`memlayout.h:105` 把物理内存上界设在 4MB，
而 `Makefile:132` 给了 `-m 128M`。
`kinit()`（`kalloc.c:30-35`）只把 `kernel_end ~ PHYSTOP` 挂进 `freelist`，
**剩下 124MB 完全没人知道。**
- **好处**：`-m 128M` 给内核留了"安全垫"，不会一超界就撞到设备地址。
- **坏处**：如果你的实验（比如 lab4 内存分配）想多要内存，
**必须先改** `PHYSTOP`，否则 `kalloc` 会一直返回 `NULL`。
- **你要学的**：**"能被验证的东西"和"看起来对的东西"之间的差距。**
这个缺陷之所以安全，是因为它**恰好没撞上任何边界**。

### H.1 你带走了什么

**三样东西：**

1. **一条完整的链路**：从 `0x1000` 的复位向量，到 `sbi_shutdown()` 的 `ecall`。
  **lab1 之后，你看任何一段内核代码，都知道"它在链路的哪一段"。**
2. **一套"五层拆解法"**（道法术技器）+ **一张"现象指纹"表**。
  **前者用来设计，后者用来调试。**
3. **一种态度**：**"能从源码算出来的数字，一律现场算"**。
  `kvminit()` 是 8 条不是九条、`initcode` 是 52 字节不是 56、
   `main()` 是 15 个不是 12 个 —— **这三个数字，都是"凭印象写必错"的典型。**

### H.3 最后一句

**你敲下的那个** `halt`**，只有一行代码。**

但它背后是：

- 一条跨越 **三次特权级**（U → S → M）的请求；
- 一张跨越 **两级页表**（用户表 / 内核表）的地址空间；
- 一套跨越 **四个文件**（`sysnum.h` / `usys.pl` / `syscall.c` / `sysproc.c`）的一致性约定；
- 以及一个跨越 **四十年** 的设计共识：
**"用户不能直接关机 —— 不是技术做不到，是不该让它做。"**

**这就是操作系统。欢迎入门。**
